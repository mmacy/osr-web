# Spec: adopting the authored layer

Status: reviewed
Owner: unassigned
Tracking issue: mmacy/osrlib-python#41 (delivery-order item 2)
Depends on: osrlib ≥ 1.6.0 — published 2026-08-08, and the floor `pyproject.toml` declares since phase 2, that being the first osr-web code to read fields no earlier release has. The authored layer itself shipped in 1.5.0; objective display names (mmacy/osrlib-python#65, landed as osrlib#66) followed in 1.6.0. The editable `../osrlib-python` checkout carries it and the lockfile stamps it.

## Summary

osrlib 1.5.0 ships the authored layer: gates on doors and level-placed transitions, data-authored triggers run by a library `Interpreter` the host registers, a player-visible journal, quests with lifecycle events and rewards, `SessionMode.VICTORY`, and non-battle party wipes routing to `game_over`. All of it is additive within schema version 3. The bundled document loads unchanged (verified against 1.5.0's one vocabulary break), and old saves migrate as saves always have.

osr-web adopts it in four phases: the engine's new voice reaches the transcript (registration, gate refusals, event handlers, and the rendering plumbing the new events expose as stale), the journal and quest log get UI, the two endings get screens, and the LLM narrator learns the new beats and the authored guidance channel. *The Cold Vein* grows authored content phase by phase, because the bundled document is how every UI surface triggers against the default — the same reason it carries five kinds of door.

Every phase plans from this spec. A phase that needs to cite mmacy/osrlib-python#41 or a review thread for a decision has found a spec defect; the move is to fix the spec, not improvise in the implementation PR.

## Findings the phases answer

Facts established against osrlib 1.5.0 as shipped and osr-web as it stands, then hardened by a three-lens adversarial review. File references into osrlib are relative to `../osrlib-python/src/osrlib/`.

- **Registration is one call at one choke point.** `session.register_listener(Interpreter(session))` (`crawl/interpreter.py`, key `osrlib.interpreter`). Every session route — premade, builder party, veteran import, save restore — converges on `Game.__init__` (`server/app.py:139`), which already owns the per-session accessories (lock, `Narrator`, `NarrationEngine`). Registering in `content.py` would miss the restore path; registering in both places would fire every trigger twice (`register_listener` never dedupes). Forgetting entirely is silent: the session plays, gates still work (they are in-engine legality checks), but triggers and quests never advance — and activation-less quests still show `active` in the view, permanently stuck, which is the deceptive failure mode.
- **The transcript path is listener-safe either way.** As of 1.5.0, `result.events` folds in everything listener-issued nested commands logged, each event once, in log order — so `execute_command`'s log-delta read (`server/app.py:1194`) is equivalent, and stays. Its comment's rationale ("so listener-driven follow-on events narrate too") is stale by osrlib's own changelog, which retired the delta idiom in its own example; phase 1 fixes the comment and keeps the behavior.
- **The journal and quests cross the wire with zero server change.** `PlayerView` gained `journal` and `quests` (`crawl/views.py:200,204`), and `_state` dumps the whole model — the server never enumerates view fields. The projection is player-safe by construction: active quests only, in document order; revealed objectives only (a hidden objective's id is absent, not masked); `narrative`/`speaker` strings inlined; no wiring, no rewards, no `guidance`. `QuestView` is `{id, name, narrative, speaker, objectives: [{id, name, state}]}` — an `ObjectiveView` carries its display label since 1.6.0 (`crawl/views.py:141`) — with objective `state` exactly `"incomplete"` or `"complete"`; `JournalEntry` is `{text, rounds}`, append-only, in order of discovery. The journal ships whole on every payload — accepted; it is bounded by the adventure's own length.
- **An objective has no display name anywhere.** `ObjectiveSpec` and `ObjectiveView` carry only the authored id, and three of the seven new message templates print raw ids — both objective events template `quest_id` *and* `objective_id`, and `adventure_completed` templates `quest_id` (resolvable server-side via `session.adventure.quest(id).name`; the objective ids are not resolvable to anything human). `_substitute_ids` rewrites entity ids only and cannot help. This is an engine gap, filed engine-first as mmacy/osrlib-python#65; phase 2 depends on it and no slug-prettifying workaround gets built here. **Closed by osrlib#66, in 1.6.0:** `ObjectiveSpec.name` is authored and optional, `ObjectiveView.name` carries `name or id`, the two objective events carry `name` and `quest_name`, and `AdventureCompletedEvent` carries the quest's `name` — so the templates print labels, and phase 1's quest-only fallbacks in `narrate.py` become the stale thing for phase 2 to retire. One consequence for every consumer: an unauthored objective's label *is* its id, so "did the author write a name?" is not a question a renderer may answer by comparing the label to the id.
- **A concluding quest's ending arrives twice.** `quest_completed` and `adventure_completed` are emitted back to back carrying the **same** authored completion beat (osrlib's own golden shows the doubled line), while the journal receives it once. The host renders the beat on exactly one: osr-web's rule is the beat rides `quest_completed` (uniform for every quest), and `adventure_completed` renders as the terminal fact — its name read off the event, which carries the concluding quest's `name` since osrlib#66 — no beat repeated.
- **Unhandled events render, badly.** `Narrator._render_event` falls back to `format_message` as a `mech` line (`server/narrate.py:457`), which is total — so the six new player-visible event types print engine-templated English the moment an authored document loads, raw ids included. The new types and codes: `journal_entry_added` (`session.journal.entry_added`; `text`, `rounds`), `quest_activated` (`session.quest.activated`; `quest_id`, `name`, `narrative`), `objective_revealed` / `objective_completed` (`session.quest.objective_revealed` / `.objective_completed`; `quest_id`, `objective_id`, `narrative`), `quest_completed` (`session.quest.completed`; `quest_id`, `name`, `narrative`), `adventure_completed` (`session.adventure.completed`; `quest_id`, `narrative`). `trigger_fired` and `note_recorded` are referee-visible and never cross. Quest lifecycle beats journal their display text as themselves — the lifecycle event *is* the journal beat, with no `JournalEntryAddedEvent` behind it.
- **`item_consumed` is not authored-content-gated.** `ItemConsumedEvent` (`exploration.item.consumed`; `character_id`, `item_id`) fires for gate tolls *and* for `WedgeDoor`'s iron spike (new in 1.5.0) — so the transcript changes for an existing verb the moment the dependency floor rises, in content that authors nothing. osr-web already writes its own spike line; the phase-1 handler must not double-report a wedge. A magic-item toll carries the session-scoped `instance_id` of an instance already consumed by render time — the handler degrades through `_item_labels` to the item's kind, the `use_item` precedent, and never prints an instance id.
- **The narrator's item names come from the wrong catalog.** `Narrator._item_name` resolves against `load_equipment()` — the shipped lists — so every line naming a bundled item (acquired, hauled, dropped, given, tolled, granted) prints the raw id. The engine's own resolver for authored ids is `session.effective_equipment`; phase 1 switches to it.
- **`_area()` asks the session where the party stands — the fact `LocationEnteredEvent.dungeon_id` (new in 1.5.0) exists to replace.** Rendering happens after the whole command completes, so a trigger consequence that relocates the party (`place_party`) makes every area event in the delta resolve against the destination; the whole-log re-render on rename has the same defect across all history. Phase 1 moves area resolution onto the event's own field. **The old location walk is deleted, not kept as a fallback**: an event without `dungeon_id` — a pre-1.5.0 save's persisted area events, which deserialize with the field `None` because additive fields carry no migration — resolves to no area, and the renderer never consults the session's current location. Keeping the walk "for old saves" would preserve the broken resolution for exactly the events it claims to serve. Be exact about what "no area" renders: **nothing at all** for that event — no place header and no prose, not a place header shorn of its prose — and `seen_areas` never learns the area, so the first entry after the upgrade prints the description in full. Old saves still load and play; their pre-upgrade scrollback loses those lines, one-time and honest. If that fidelity ever matters, the move is osrlib-side load-time normalization of the event log (engine-first), never an osr-web fallback path.
- **Nothing in osr-web validates authored references.** `validate_adventure` — the walk that catches dangling item/area/monster ids, literal character ids in consequences, and the bundled-id collision rule — runs only inside `GameSession.new`, so today a typo loads clean, fails on session creation at best, and silently never fires at worst. `load_adventure` and `library.add_adventure` (whose docstring already promises whole-document validation) both gain the call in phase 1. Collisions also raise from `GameSession.__init__` on the *restore* path, for doctored saves.
- **The interpreter's failure modes are silent by design, and osr-web has no referee channel.** A rejected consequence or an unlandable reward is dropped individually and recorded via `RecordNote`; a cascade past depth 4 truncates into notes; all of it rides referee visibility, which the narrator correctly discards. Phase 1 routes `trigger_fired` and `note_recorded` to the `osr_web` server log — the operator's terminal is the referee's screen; the wire never carries them. This is also the only consumer a trigger's authored `fired` beat gets.
- **Gate refusals arrive with the author's words, and osr-web throws them away today.** `exploration.door.gate_refused` (`OpenDoor`, `ForceDoor`) and `exploration.transition.gate_refused` (`UseStairs`) are the only gate-refusing codes; the authored line rides `rejection.params["refusal"]` (present only when authored). `rejection_text` (`server/narrate.py:98`) reads only the code, so an unmapped code today prints as its literal string. Gates check last, after every mundane refusal, and cost nothing: no die, no time, no noise, no wandering third; the engine appends no events on any rejection, so `observe` receives an empty delta and returns. Success beats ride the successful command's own event (`DoorEvent.narrative`, `LocationEnteredEvent.narrative`) — but only when a transition crosses a level or dungeon boundary; a same-level transition emits no arrival event and drops the beat (and a toll on one charges silently), so bundled gated transitions must cross a boundary. A gate's `journal` beat has no consumer at all — don't author one. A shut gated door refuses `MoveParty` with the ordinary `exploration.move.blocked`; a door standing open admits passage unchecked until it closes. The app.py rejection assembly prefixes a speaker name only when `params` carry `character`/`caster`, which gate refusals don't — the authored line survives verbatim; phase 1's test pins that.
- **`"victory"` soft-locks the client today.** No crash: `render()` completes, the HUD chip reads "victory", but the action bar empties, `#context` and the town board go blank, the keyboard handler returns, and no overlay ever shows — a live-looking screen with no verbs. The gameover screen, by contrast, is mode-driven (`static/app.js:662`), which is why **non-battle wipes need zero client work** — any route into `game_over` already lands on the overlay, including `boot()` restore. `SessionMode.terminal` covers both endings; `PlaceParty` stays legal in `game_over` (the raise-dead salvage door) but is illegal in `victory`, and `SpawnMonsters`/`SpawnNpcParty` are illegal in both.
- **Victory has exactly one entrance, and it is the command, not the interpreter.** `CompleteQuest` on a `concludes_adventure` quest **in a non-terminal session** clears any open encounter or battle, sets `victory`, and emits `QuestCompletedEvent` then `AdventureCompletedEvent` — a party that finishes the job after it has already fallen completes the quest and gets no ending event. The interpreter is the only issuer in an authored session and the only thing that pays rewards; rewards land *after* the transition, so an authored reward set must be terminal-legal (`grant_item`, `grant_coins`, `award_xp`, `set_flag` are; spawns are not, `place_party` is not), and an `award_xp` reward can emit level-up events *after* the ending event — the victory screen and the closing beat both tolerate that ordering.
- **Winning ends commerce on the spot.** The instant the concluding objective completes — typically on the homecoming town entry — every play command is illegal, selling and healing included. Treasure XP is unaffected (it awards on the town arrival itself, valuation delta, in the same accepted command), so a stranded haul costs coins-on-hand, never advancement. osr-web accepts the trade: no two-trip choreography is imposed, the authored rewards can carry the story's payment (`grant_coins`), and the victory screen presents the carried fortune as part of the tale, not as a bug.
- **Authored beats are the table's words; `guidance` is steering that never prints.** A `NarrativeBlock`'s display beats (`refusal`, `success`, `offer`, `progress`, `completion`) render verbatim — osrlib's downstream instruction to LLM narrators is to weave around them, never paraphrase them. The beat-to-consumer mapping is exact and partially empty: `progress` is read on an **objective's** block and unread on a quest's; `completion` the reverse; a gate's `journal` beat reaches nothing. `guidance` rides every narrative block plus the per-level `LevelSpec.guidance` ambient slot, with osrlib's stated windows: quest active, gate encountered, trigger fired, level occupied. It surfaces on no event and no view — a narrator reads it off the adventure document server-side, and it must never cross the wire or print as written. A trigger's firing is only attributable through the referee-visible `trigger_fired` event (`JournalEntryAddedEvent` carries no trigger id).
- **Saves are safe; imported *items* are the leak.** `fired_triggers`, `journal`, and `quests` are engine-owned top-level state blocks; `save_game`/`load_game` round-trip them with no host involvement, pre-1.5.0 saves load with empty/seeded state, and none of the blocks reference a character id — `party_from_save` imports nothing from them. But the imported party keeps its inventory, and `has_item` is stateless and party-wide (every member, living or dead, worn slots included): a veteran carrying adventure A's key or relic pre-satisfies adventure B's gates and quest conditions — or its own adventure's, on re-import. Phase 1 sets the import policy: instances whose template id is not in the shipped catalogs are stripped on import, alongside the conditions and modifiers already stripped — adventure-bound objects stay with their adventure. Two accepted save facts ride along: a save embeds the adventure document it was playing, so a pre-content save of *The Cold Vein* can never fire the new triggers or win (no save upgrading, by design), and a `victory` save is unreadable by pre-1.5.0 engines (osrlib's documented accepted risk for a new enum value).
- **The shop carve-out is already respected, minus two strings.** `PurchaseEquipment` stocks the shipped lists only; a bundled id refuses the whole command with `items.purchase.not_stocked`, distinct from `session.command.unknown_item` — and *neither* is in `_REJECTION_TEXT` today. Bundled items are found, granted, or taken from caches — never bought — and their authored `cost_gp` is conventionally `0` and must not render as a price. A bundled id in the party builder's purchase step rejects as `creation.item.unknown` (the builder catches the engine's `ValueError`); the wizard's catalog is the shipped lists, so no builder change.
- **Document-loading edges, settled empirically.** An adventure document's envelope is checked (`kind`, `schema_version <= 3`) but never migrated — the 2→3 migration walks a *save* shape — and `Adventure` ignores unknown keys. So a schema-2 stamp on a document carrying `items`/`triggers`/`quests` loads fine on 1.5.0 — and is silently stripped to an unwinnable shell by a pre-1.5.0 engine. Phase 1 therefore re-stamps `content/adventure.json` to `schema_version: 3` / `engine_version: "1.5.0"` (so an old engine refuses loudly with `SaveVersionError` instead) and updates `content/README.md`'s pinned stamp. A third-party schema-2 document using the one vocabulary 1.5.0 removed is permanently unloadable while the metadata-only scan still lists it — accepted; the load failure is already a clear 422.
- **The screenshot harness never plays the bundled document.** Captures run *The Hollow Tithe* (`tests/assets/capture-adventure/`), by design — so phase 1's bundled content moves no shot, and a quests card reaches the README only if phase 3 authors a quest into the *capture* document too and extends the shot's assertions. What phase 1's content can disturb instead: AGENTS.md's documented scripted route to the first fight, and the unit tests that build sessions over the bundled document — all of which start running the interpreter the day `Game.__init__` registers it.
- **The dependency floor is for consumers of the published package.** `[tool.uv.sources]` keeps resolving the local editable checkout regardless of the floor; the `>=1.6.0` constraint documents the contract and guards a future un-vendored install, nothing more. Nothing here will ever observe it being wrong, so it has to be reasoned about when it moves.
- **Authoring references, for the content work:** osrlib's `examples/tui_crawler/content.py` (bundled item, fetch quest, cache placement, level guidance), `tests/crawl_fixtures.py` (gated and barrow adventures), and the goldens `phase11_gates.json` / `phase13_journal.json` / `phase14_triggers.json` / `phase15_quest.json` for exact wire shapes — note the goldens are run dumps (`command_log`, `event_log`, `final_state`), **not** loadable adventure documents, and osrlib ships no quest-carrying adventure JSON at all; phase 2's fixture recipe below exists because of that. The condition union is `has_item` (whole carried surface, living or dead; `consumes: true` is the toll form, first holder in marching order pays per success), `flag_equals` (strict; absent matches nothing), `effect_active`. Trigger consequences are a closed command union addressing `@party`/`@first` — a literal character id is caught by `validate_adventure`, not by the models. Objective completion matching is edge-triggered: a completion suppressed by the cascade bound waits for the *next* matching event, not a retry.

## Design constraints

- **The wire contract holds, unweakened.** `view.journal` and `view.quests` are the player projection — they cross because the engine already projected them player-safe. `guidance`, `trigger_fired`, `note_recorded`, fired-marks, quest wiring, and anything reached through `RefereeView` never cross, and no referee-view endpoint exists or will. New response fields keep asking the standing question first.
- **osrlib owns every rule — and we own osrlib.** osr-web registers the interpreter and renders what comes back. It never matches a trigger pattern, never evaluates a condition, never decides an objective completed, never routes to victory. The fence has a gate that swings engine-ward: when a phase needs data or behavior the engine doesn't expose, the move is to extend osrlib-python — in engine scope, greenfield, with its own tests and docs — or file the osrlib issue for another agent to land first, *before* any osr-web implementation that would otherwise work around the gap (worked precedent: mmacy/osrlib-python#65, objective display names, which gated phase 2 and landed as osrlib#66 before phase 2 began). A downstream need discovered late is an engine gap found, never a license to re-implement or approximate a rule here.
- **Authored beats verbatim.** Everywhere authored text appears — rejection lines, transcript entries, panels, prompts — it renders as written. The deterministic transcript may set a fact beside it, never rewrite it. An authored refusal rides the standard rejection line (the ✕ mono voice *is* the referee saying no); this is settled — phase plans don't relitigate the voice.
- **The bundled document exercises every surface**, and `content/README.md`'s provenance and feature-index contract is updated in the same PR as any document change. New content stays original work, referencing only osrlib's OGL SRD catalogs by id.
- **The chrome stays quiet.** New UI picks from the existing tokens and voices: authored narrative in the serif referee voice, mechanics in mono, interface in system sans. Journal and quest surfaces follow the standard-patterns rule — boring controls, flavor only in content.
- **Each phase carries its own tests, docs, and `AGENTS.md` facts.** No trailing validation or documentation phase. Client changes bump `app.js?v=N`. A phase that moves what a README screenshot shows recaptures it.

## Phase 1 — the engine's new voice reaches the transcript

The server-side adoption, whole: after this phase the engine's authored layer runs and everything it says reaches the player correctly, before any of it gets dedicated UI.

- `pyproject.toml`: `osrlib` → `osrlib>=1.5.0` (editable path source unchanged), `uv sync`.
- `Game.__init__` registers `Interpreter(session)` — once, covering all four session routes. Nothing registers anywhere else, and replay is not a thing osr-web does. The stale log-delta comment at the render site is corrected (behavior unchanged).
- `load_adventure` and `library.add_adventure` run `validate_adventure` — authored-reference typos fail at load/upload with a friendly 422, not silently in play.
- `rejection_text` learns params: a rejection carrying `params["refusal"]` renders the authored line verbatim (the code's mapped text does not compete with it). `_REJECTION_TEXT` gains `exploration.door.gate_refused` and `exploration.transition.gate_refused` fallbacks for the unauthored case, plus `items.purchase.not_stocked` ("the trader doesn't carry that" flavor) and `session.command.unknown_item`.
- `narrate.py` handlers for every new player-visible event: `journal_entry_added`, `quest_activated`, `objective_revealed`, `objective_completed`, `quest_completed`, `adventure_completed`, `item_consumed`. Authored `narrative` text renders in the prose voice (the module speaking); the templated fact stays in the system voice. The completion beat renders once, on `quest_completed`; `adventure_completed` renders the terminal fact, its quest named off the event. Objective lines carry the authored beat when present and otherwise name the objective and its quest off the event — never a raw id fished out of the wiring fields, and never a label second-guessed by comparing it to the id. `item_consumed` covers the toll *and* the wedge spike without double-reporting the existing wedge line, and degrades a consumed magic instance through `_item_labels` to its kind, never an instance id. The door and location handlers append the new `narrative` success beats. `_area` resolution moves onto `LocationEnteredEvent.dungeon_id`. **Door-edge trap finds keep the bearing-less "a hidden trap".** This bullet originally called for naming the door (1.5.0 widened a `room_traps` search to the searched cell's door edges), and adversarial review reversed it for the same reason `_area`'s fallback was deleted: `SearchCompletedEvent` carries no position, so a render-time reconstruction reads the party's *current* cell, which on any whole-log re-render — reload, rename, restore — is not the searched one. Reproduced against the bundled document: a trap found underfoot ("a hidden trap") re-rendered from the corridor as "a trap rigged to the south door", a bearing the engine cannot produce for an enter-trigger trap at all. The walk also could not honour `_reveal`'s own guards (an undiscovered secret door, `trigger == "open"`), so it could point at hidden geometry. **The renderer states what the event states.** The bearing is the engine's to state — filed as mmacy/osrlib-python#67 — and there is no interim reconstruction; `_found_phrase` stays a module function taking a token alone, so it cannot reach a session even by accident. The module header's stale kind list is fixed in passing.
- Referee observability: `trigger_fired` and `note_recorded` log to the `osr_web` logger — dropped rewards, truncated cascades, and fired wiring reach the operator's terminal and nothing else.
- Import policy: `party_from_save` strips item instances whose template id is not in the shipped catalogs, alongside the conditions and stat modifiers it already strips — adventure-bound objects stay with their adventure.
- Bundled content, so the surfaces fire against the default: *The Cold Vein* gains one bundled item (`Adventure.items`, placed by id via a cache's `item_ids`), one gated door keyed to it with authored `refusal`/`success` beats — **non-consuming**, so the key remains a keepsake (the toll form is exercised in tests; the document carries no toll, recorded in the README) — sited as a shortcut or side room, never the only route, and one non-repeatable trigger (an `area_entered` journal beat is the natural first) exercising the `fired` and `journal` forms. The document re-stamps to `schema_version: 3` / `engine_version: "1.5.0"`. `content/README.md`'s shape, stamp, and feature-index sections updated in the same PR. `FeatureSpec.magic_item_ids` is deliberately unused for now; the README records the deferral.
- Tests, in the house styles: gate refusal renders the authored words and never the code string, unprefixed by any speaker; the trigger's journal line lands in the transcript and in `view.journal`; a bundled id renders as its display name in acquisition and haul lines; a wedge reports one line; the ending renders its beat once across the two terminal events; save/restore keeps `fired_triggers`/`journal`/`quests` and re-registers the interpreter (one registration, one firing); `validate_adventure` runs over the bundled document; the existing bundled-document unit tests and AGENTS.md's scripted route to the first fight still hold with the interpreter registered. `TestHandlersReadRealFields` auto-covers the new handlers.

Milestone: driving the default adventure over HTTP, the gated door refuses with the author's sentence, opens once the key is carried, and the success beat reads correctly; the trigger fires once, its journal line in the transcript; a save made after all that restores with the same journal and fired state.

## Phase 2 — the journal and the quest log

The client renders what phase 1 put on the wire. The engine gap that blocked it — mmacy/osrlib-python#65, objective display names, since the card will not render authored slugs — closed as osrlib#66 while phase 1 was in flight, which leaves the phase two pieces of server work beside the client's: raising the dependency floor to `osrlib>=1.6.0`, the first release carrying the fields this phase reads, and retiring phase 1's workaround for the gap in `narrate.py` (the two objective handlers, `_on_adventure_completed`, and `Narrator._quest_name`, which the events' own `name`/`quest_name` make redundant).

- A quests card, rendered from `view.quests`: quest name, the `offer` narrative attributed to its `speaker`, and the revealed objectives by name with their states. While exploring it hangs off `renderContext`'s exploring branch (its own card beside "This area", not appended to another card's tail); in town it is its own card on the town board — placed and worded so it never reads as an index of the rumors, which the engine deliberately gives no mechanical linkage to quests. The card is simply absent when no quest is active; nothing reserves height for it.
- The journal, summoned like the map but present in **every** mode, town included: an overlay on `J` with a Journal button in the topbar (the automap's markup, toggle, and Esc precedence as the model; the availability rule deliberately wider than the map's dungeon-only gate), rendering `view.journal` in order — it grows for the life of an adventure, and the rail is the wrong home for an unbounded list: it scrolls, but its scrollbar is deliberately near-invisible (`scrollbar-width: thin` over a transparent track), so a card that outgrows the viewport would simply look truncated. A repeatable trigger appending identical lines is rendered as the record it is. Entry `rounds` render as in-world time (one dungeon turn is 60 rounds), presentation settled in the phase plan.
- `app.js?v=N` bump, and a screenshot recapture. No *new* shot: captures run *The Hollow Tithe*, which carries no quest and no journal content, so a quests card would not render and a journal shot would photograph its empty state — the capture-document decision belongs to phase 3. But four of the six existing shots move anyway, because the journal's entry point is in the topbar and `.scrim` is only 62% opaque over a topbar that is a plain flow element: `play-view`, `character-sheet`, `automap`, and `combat-round` all show it, and phase 2 recaptures them.
- Fixture: osrlib ships no quest-carrying adventure JSON, so this phase checks one into `tests/assets/` — generated once, from the osrlib checkout, as `stamp_document("adventure", build_barrow_adventure().model_dump(mode="json"))` (`tests/crawl_fixtures.py`; the barrow already carries a town, an entrance, a bundled item, a trigger, and a concluding quest), with the recipe recorded in `tests/assets/README.md`, that directory's provenance home, because JSON carries no comments and there is no header to write it in. Driven via `OSR_WEB_ADVENTURE` in the tests; a manual drive wanting both documents in one library uses the appending `OSR_WEB_ADVENTURES` instead.

Milestone: with the barrow fixture, the offer reads in the card in the speaker's voice, objectives appear by name and tick from incomplete to complete, hidden objectives are absent until revealed, and `J` summons the full journal — in town and in the dungeon.

## Phase 3 — endings: victory and the fallen

Both terminal modes end the game like they mean it, and the default adventure can actually be won.

- A `victory` screen in the gameover screen's exact mold: its own branch in `showScreen`, the mode-driven trigger beside the `game_over` one in `render()`, the `boot()` restore path, Esc-terminal like `gameover`. The gameover pair of actions (roll a new party into the same adventure; return to the title) plus a third, victory-only: **Save the party** — the topbar is unreachable under the overlay and Esc is the floor, so without it the one party that finishes an adventure alive is the one party the veterans flow can never import; the gameover screen deliberately gets no counterpart, because a wiped roster imports as corpses and its salvage door stays the referee's `PlaceParty`. The voice is triumph, the accent amber — treasure light, not danger red. The card carries the adventure's journal — the tale, told, readable right there (the game screen underneath is unreachable once the overlay is up) — and presents the party's carried fortune as part of the ending, because commerce is over the moment victory fires: treasure XP already awarded on the homecoming arrival, so the unsold haul is the retirement purse, not a bug. The HUD chip stops reading like a bug.
- Non-battle wipes: no client change (the mode-driven gameover check already catches every route into `game_over`), but the phase verifies it end to end — a trap or deprivation wipe lands on the gameover screen, not a soft-lock.
- The rail-furniture question phase 2's plan measured and willed here is answered in this phase, because authoring the concluding quest is what turns "the third `#context` card is below the fold" from a fixture-only state into the shipped default's normal exploring state. The answer, its measurements, and its residuals are the phase plan's (`phase-3-plan.md`, the viewport letterbox).
- Anywhere the client asks "has this session ended" branches on one shared two-mode constant beside the screen-state machine, mirroring `SessionMode.terminal`, rather than string-matching `game_over` alone.
- Bundled content: *The Cold Vein*'s concluding quest — with an **authored activation** (an activation-less quest surfaces through no event, no journal line, and no beat: its offer would stand silently in the view alone), at least two objectives with `completion: "all"` and an `item_acquired` spine on a **new second bundled item** (the phase-1 key is a gate key, not the quest relic; and the all-rule plus the acquisition spine is what keeps an imported or carried-in relic from short-circuiting the quest), a `town_entered`-with-`has_item` homecoming, authored `offer` and `completion` beats with a `speaker` on the quest block and `progress` beats on the objectives (where they are actually read), rewards addressed to `@party`/`@first` from the terminal-legal set (`grant_coins`, `award_xp`, `set_flag` — a reward-triggered level-up's events landing after the ending is expected), `concludes_adventure: true`. ## Phase 4 — the narrator learns the authored layer

LLM narration catches up with the new beats and the guidance channel. This phase **amends `specs/llm-narrative/spec.md` in the same PR**: the guidance channel is a deliberate, named exception to its design principle 2 ("prompts built exclusively from material that already crosses the wire") — one referee-only steering block, marked never-to-be-quoted, mitigated by the existing output sanitation — so principle 2, the prompt-design section, and the "prompts contain only player-visible material" acceptance criterion are rewritten to name it, and AGENTS.md's narration bullet gains the fact. Player safety moves from purely structural to structural-plus-instructed for exactly this one block; everything else about the older spec still governs.

- New beats, each an emphasis that is a tone **plus a limit**: `adventure_completed` (a triumphant closing paragraph, at the **top of the `BEATS` table** — rewards resolve in the same command and a reward-triggered level-up would otherwise out-prioritize the ending), `quest_activated` (the offer in the speaker's voice), `quest_completed`. Whether `objective_completed` earns a beat of its own or stays a transcript line is the phase plan's call — the queue coalesces, but not every line deserves prose.
- The verbatim discipline reaches the prompts: authored beats arrive through the transcript (`just_now`), and the new emphases say what the model may do with them — deliver the authored words as written and put its creativity around them, never over them. Any truthfulness problem is fixed in the transcript, never by widening `build_prompt`.
- One steering channel for every carrier: `build_prompt` gains a single keyword-only `guidance: str` parameter, rendered as a referee-steering block the prompt marks as never-to-be-quoted. `observe`, already under the game lock and already handed the raw event delta, assembles it from the carriers in play at that beat, each read off `session.adventure`: the occupied level's `LevelSpec.guidance`; every active quest's block `guidance` (osrlib's window for a quest is *while active*, not just the quest's own beats), with a revealed-but-incomplete objective's block riding along with its quest — that objective window is osr-web's own rule, since osrlib names none for objectives; the block `guidance` of any trigger whose `trigger_fired` event is in the run being narrated (a referee-visible event inspected server-side only); and a door gate's block `guidance` when the run carries its success beat (`DoorEvent.narrative`), mapped back through the edge the event names — the event carries the party's cell and the command's direction, and an edge resolves the same from either side. A gated *transition*'s success beat rides the arrival's `LocationEnteredEvent`, which names where the party arrived and nothing about the crossing it took, so no honest mapping back to the transition spec exists; transition-gate guidance waits on the engine naming the crossing (engine-first — the osrlib issue phase 4 files) rather than any reverse search over the document's transitions. The bundled gate is a door, so the shipped document loses nothing. Under coalescing, guidance is per-snapshot and the merged prompt concatenates the batch's blocks in beat order, deduplicated — a coalesced trigger's steering is neither dropped nor carried past its window. Scattering steering across `location_line` and the emphasis strings would hide the fence; one named channel keeps "never crosses the wire, never prints as written" auditable in one place.
- Gate refusals are deliberately not narrated. A gate-refused command emits no events — an empty delta; `observe` returns immediately — so steering that moment would mean building narration-on-rejection machinery for a moment whose authored refusal line already renders verbatim in the transcript. If prose there ever proves wanted, that is new pipeline design to spec on its own, not a forgotten wire in this phase.
- The structural strings-only test keeps passing by its letter; this phase rewrites its comment to say what it now proves (no session or event objects reach the builder) and adds the tests the new block earns: the never-quote marker wraps it, and the coalescing merge rule holds.
- Bundled content: authored `guidance` for *The Cold Vein* — both dungeon levels' ambient slots, the concluding quest's block, and the phase-1 gate's and trigger's blocks — written as steering, not script, so every plumbed carrier is exercised against the default document.
- Tests in `tests/test_narration.py`'s established shapes: one detection test per new rule plus priority tests against the neighbouring rules (including `adventure_completed` over `leveled_up`), and prompt tests pinning each carrier's window — level guidance while occupied, quest guidance while active, trigger guidance only in its firing run, gate guidance only on its success — and that the assembled block reaches the prompt as steering while the authored beat text arrives untouched and nothing in it ever crosses the wire.

Milestone: with the narrator on, entering a guided level colors the passage the way the author steered it; a run in which the phase-1 trigger fires carries that trigger's steering and no other's; completing the adventure yields a closing passage that keeps the authored completion line's words and facts intact.

## Sequencing

Strictly 1 → 2 → 3 → 4. Phase 2 renders what only phase 1 can put on the wire and is additionally gated on mmacy/osrlib-python#65, which can land in parallel with phase 1; phase 3's victory needs phase 1's registration and adds its own relic; phase 4 narrates events phase 1 handles and content phase 3 authors. There is no parallel track worth the coordination cost at this size.

## Non-goals

- No referee view, no referee endpoint, no quest wiring, hidden objectives, rewards-in-advance, or `guidance` on the wire — under any flag. The referee's channel is the server log.
- No client-side rule work: no condition evaluation, trigger matching, or completion logic in `app.js`.
- No new API endpoints. The journal and quests ride the existing payloads; the existing polling narration channel stays as is.
- No persistence changes: saves remain pure osrlib documents (plus the existing `name` key); passages stay in-memory per `specs/llm-narrative/spec.md`. No save upgrading — a save plays the adventure it embeds.
- No rumor-to-quest linkage, implied or built: `Adventure.hooks` stays inert prose by the engine's own ruling, and the town board's layout keeps the two surfaces visually distinct.
- Post-victory play, campaign continuity, NPC entities, accept/decline on quests, pack quests, mid-battle boss triggers, trap `bypass` conditions, condition-keyed prose variants — engine non-goals and deferrals, mirrored here.
- osr-editor's adoption (types, ops, quests panel, lint battery) — its own repo, its own issue.
