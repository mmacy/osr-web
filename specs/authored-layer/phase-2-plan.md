# Phase 2 plan — the journal and the quest log

Implementation plan for phase 2 of [the authored-layer spec](spec.md): the client renders what phase 1 put on the wire — a quests card in the rail and on the town board, and a journal overlay summoned in every mode. Milestone: with the barrow fixture, the offer reads in the card in the speaker's voice, objectives appear by name and tick from incomplete to complete, hidden objectives are absent until revealed, and `J` summons the full journal — in town and in the dungeon. Two things changed since the spec was written. The blocker cleared: mmacy/osrlib-python#65 landed as osrlib#66, so `ObjectiveView.name`, `ObjectiveRevealedEvent.name`/`.quest_name`, `ObjectiveCompletedEvent.name`/`.quest_name`, and `AdventureCompletedEvent.name` all exist — but on osrlib **main**, not in any release, which makes this phase's dependency floor a decision rather than a formality (and, by osrlib's own SemVer policy, a 1.6.0 rather than the patch it first looks like). And two spec sentences that change what the phase does turn out to be wrong: "No server change is expected in this phase at all" (phase 1 coded around the missing objective names and left a comment citing #65; that workaround is now the stale thing) and "The README screenshots stay unchanged" (a Journal button in the topbar moves four of the six shots — measured, not reasoned). Both are corrected in `spec.md` on this branch, along with four staler slips the same research turned up.

## Spec corrections, made in this PR

The spec's own rule is that a phase which finds a spec defect fixes the spec rather than improvising around it, and phases 3 and 4 read the same document. So `spec.md` is amended here, on this branch, in six places:

- The **depends-on line** and the **objective-display-name finding**: osrlib#65 closed as osrlib#66 and ships in 1.6.0. The finding gains the consequence every consumer inherits — an unauthored objective's label *is* its id, so no renderer may ask "did the author write a name?" by comparing the two.
- The **phase 2 paragraph**: "no server change is expected in this phase at all" was true only while the engine gap was open. Retiring phase 1's workaround is server work, and so is the floor.
- The **phase 2 screenshot claim**: "the README screenshots stay unchanged" holds for the quests card and fails for the topbar. Measured, not reasoned — see work item 8.
- The **engine-first constraint's parenthetical**, which described mmacy/osrlib-python#65 in the present tense as still gating.
- The **journal bullet's "the rail has no scroll affordance"**, which work item 3 measures as wrong: `.rail` is `overflow-y: auto` (`style.css:105`). The point the clause was reaching for survives and is now stated — the rail's scrollbar is deliberately near-invisible, so an unbounded list *looks* truncated there, which is the real reason the journal is an overlay.
- The **ending-arrives-twice finding's name source**: "quest name resolved off the document" was how `_on_adventure_completed` had to work before the event carried a name. osrlib#66 put the name on the event, work item 2 moves the handler onto it, and the finding now states that — the same correction the depends-on line and the objective-display-name finding already take, in the one sentence the first pass missed.

**Six more** the implementation and its reviews found, corrected in `spec.md` on the implementation branch and recorded here so the count stays honest. Four are facts this phase retired:

- the phase 2 **fixture bullet's "recipe recorded in the fixture header"**, which this plan's work item 6 already overrules (JSON carries no comments, so there is no header — the recipe goes in `tests/assets/README.md`);
- the **depends-on line**, which still opened "osrlib ≥ 1.5.0" as the standing floor after work item 1 raised it to 1.6.0;
- the **phase 1 roadmap bullet**, which still described `adventure_completed` as naming its quest "off the document" and parenthesised objective naming as waiting on osrlib#65 — the same two facts work item 2 retires, in the sibling sentence the first pass corrected at the findings list but not in the phase 1 section;
- the **dependency-floor finding**, which still quoted `>=1.5.0` as the constraint `pyproject.toml` carries.

One is a wire shape phases 3 and 4 would have trusted: the **journal-and-quests finding** gave `QuestView` as `{…, objectives: [{id, state}]}`, but an `ObjectiveView` has carried `name` since 1.6.0 (`crawl/views.py:141`) — the shape `tests/test_quest_log.py` now pins, and a shape that contradicted the objective-naming correction one line below it.

One is a citation that rotted inside this branch: the victory-soft-lock finding pointed at **`static/app.js:653`** for the mode-driven gameover check, which work item 4's three inserted lines moved to 662.

Form note, from the duck: the amended paragraphs state the **current** design rather than quoting the sentences they replace. A spec that carries its own changelog is a spec phases 3 and 4 have to read twice, and git history is this repo's archive. What each correction *was* lives here, in the plan that found it.

## Scope

In scope:

- The osrlib 1.6.0 floor, and the release that makes it true
- Objective and quest display names in the transcript — the phase-1 workaround retired
- The quests card, in the exploring rail and on the town board
- The journal overlay, its topbar button, and the `J` key
- The barrow fixture, its provenance note, and server-side pins for the quest projection
- Recapturing the four screenshots the topbar button moves
- The `AGENTS.md` sentences this phase falsifies

Out of scope:

- **The victory screen, and anything that reaches `SessionMode.VICTORY`.** Phase 3. The barrow fixture is chosen partly because no *player* command can conclude its quest (work item 6), so the drive this phase prescribes can never land on the soft-lock the spec documents.
- **Quest content in *The Cold Vein*.** Phase 3 authors the concluding quest and its second bundled item. The bundled document carries no quest in this phase, which is exactly why the fixture exists.
- **A quests card or journal shot in the README.** Declined here, not deferred to a later plan's discretion: the capture document is *The Hollow Tithe*, which carries zero triggers, zero quests, and zero items (measured), so a journal shot would photograph the empty state and a quests card would not render at all. Giving the capture fixture authored content is a capture-fixture change the spec already assigns to phase 3; doing it here would churn the same fixture twice.
- **A quests card in encounter or battle mode.** Declined: `renderContext` branches by mode and the phase leaves the encounter and battle branches alone. The rail is contested space during a fight, and the standing charge is not the thing the player needs while declaring attacks.
- **Any new API endpoint, or any change to what crosses the wire.** Declined in the spec's non-goals. `view.journal` and `view.quests` already cross because `_state` dumps the whole player projection; the server change in this phase is to `narrate.py`'s rendering only.
- **Client-side collapsing of repeated journal entries.** Declined: `appendLog`'s `×N` collapse is a transcript reading affordance, and the journal is the record. A repeatable trigger that wrote the same line twice wrote it twice.
- **Narrating the new beats, and the `guidance` channel.** Phase 4.

## Work items

### 1. The dependency floor — `pyproject.toml`, `uv.lock` (prerequisite in `../osrlib-python`)

- **Prerequisite, in the osrlib repo and not in this PR: cut 1.6.0.** osrlib#66 is merged to main and sits under `## [Unreleased]` in its `CHANGELOG.md`; `pyproject.toml` there still reads `version = "1.5.0"`. The release ritual is the one `af5efd7`/`b81c36d` followed for 1.5.0 — version bump, the changelog's `[Unreleased]` section promoted, tag `v1.6.0`. Note what the tag does: `.github/workflows/release.yml` fires on `tags: ["v*"]` and publishes to PyPI, so this is an outward-facing act and belongs to its own repo and its own decision. It is a **merge gate** for the implementation PR — the plan PR waits on nothing — and not a build gate for the work.
- **It is a minor, not the patch it first looks like.** The changelog declares SemVer adherence (`CHANGELOG.md:5`) and `[Unreleased]` carries `### Added` and nothing else — `ObjectiveSpec.name`, `ObjectiveView.name`, four new event fields. Added functionality is a MINOR bump, and osrlib's own history is unbroken on the point: every release with an `### Added` section (1.5.0, 1.4.0, 1.3.0, 1.2.0, 1.1.0, 1.0.0) took a minor, and the sole patch (1.2.1) is `### Fixed` alone. Worth getting right before the tag, because a published version number cannot be withdrawn and this one propagates into `pyproject.toml` and into the shared spec that phases 3 and 4 read.
- Then here: `osrlib>=1.5.0` → `osrlib>=1.6.0` (`pyproject.toml:7`), `uv sync` to refresh `uv.lock`. The `[tool.uv.sources]` editable path entry is untouched.
- Rationale: phase 2 is the first osr-web code that *reads* fields published 1.5.0 does not have — `ObjectiveView.name` in the card, and `name`/`quest_name` on the two objective events plus `AdventureCompletedEvent.name` in `narrate.py`. A floor of `>=1.5.0` would be a false promise of exactly the kind phase 1 refused when it re-stamped `content/adventure.json` to `schema_version: 3`: better a loud refusal than a silent stripping.
- **Hazard, and the reason this is easy to get wrong:** `[tool.uv.sources]` resolves the local editable checkout regardless of the floor, so a wrong floor never fails locally, never fails in CI, and never fails a test. Reproduced during review: a throwaway project declaring a floor the published package does not satisfy, against the same editable path source, locked and synced clean at `osrlib==1.5.0`, no warning, with the specifier dropped from the lock's `requires-dist`. The constraint has to be reasoned about, because nothing will ever observe it here.

### 2. Objective and quest names reach the transcript — `server/narrate.py`, `tests/test_narrate.py`

- `_on_objective_revealed` and `_on_objective_completed` currently render the authored beat when there is one and otherwise name only the quest, because when phase 1 was written an objective had no display name anywhere in the engine. The events now carry one. The unauthored fallbacks become, in the system voice already established by `New quest: {name}.` and `Quest complete: {name}.`:
  - revealed → `New objective: {event.name} — {event.quest_name}.`
  - completed → `Objective complete: {event.name} — {event.quest_name}.`
- `_on_adventure_completed` reads `event.name` instead of resolving the quest off the document. Its wording is unchanged (`The adventure is won — {name} is done.`); only the source of the name moves. The handler's comment says "this event carries no name of its own", which is now false and goes with it.
- **`Narrator._quest_name` is deleted.** Those three handlers (`narrate.py:1137`, `1145`, `1164`) were its only consumers, and every one of them now has the name on the event. Greenfield: no helper kept because it still compiles.
- **The deletion cascades further into `tests/test_narrate.py` than it first appears, and the whole chain goes.** Measured: `_adventure` (line 1181) has four callers — 1236, 1253, 1266, 1280 — three passing `quests` positionally and one (1266) bare, and its `dungeons` parameter has **never** had a caller. Once no handler resolves a name off the document, all four call sites drop their `adventure=` argument, `_adventure` has zero callers and is deleted whole, and `make_narrator`'s own `adventure=None` parameter (line 64) plus the `if adventure is not None` branch in its body lose their last caller too — `bundled_narrator` (line 1424) builds a real session with `adventure=load_adventure()`, which is a different thing entirely. Delete the parameter and the paragraph of `make_narrator`'s docstring that explains it ("`adventure` is only needed by the handlers that resolve a quest's display name off the document"), which this change falsifies. Stopping halfway — keeping `_adventure` for the sake of a parameter that was already dead — is the "kept just in case" pattern the guide names.
- **Do not compare `event.name` to `event.objective_id` to detect an unauthored objective.** The engine fills `name=objective.name or objective.id` at emission (`crawl/session.py:1190,1220`), so for an unauthored objective the label *is* the slug — and that is the engine's own answer to what the thing is called. Testing the answer against the id we passed in is the precise anti-pattern `AGENTS.md` records for `_consumed_item_phrase`, where the comparison threw a perfectly good name away. Render what the event states; if a slug is ugly, the fix is an authored name in the document.
- **No fallback for the empty defaults.** `name` and `quest_name` default to `""` only so an event logged before the fields existed still parses. The engine always fills them at emission, and osr-web ships no quest content before phase 3, so no save in existence can carry a name-less objective event. Same rule as `_area` and the level-arrival line: the renderer states what the event states, and restoring fidelity for an older artifact is osrlib load-time normalization, never an osr-web fallback path.
- Tests: rewrite `test_unauthored_objectives_name_the_quest_and_never_its_slug` to assert the two new sentences (its name changes with its claim); delete `test_an_unresolvable_quest_id_degrades_rather_than_printing_itself`, whose branch no longer exists once `_quest_name` is gone; construct `AdventureCompletedEvent` with `name=` in the ending test. `TestHandlersReadRealFields` needs no change and covers the new field reads for free — but note the surrounding tests build events as real models, not `SimpleNamespace`, which is what makes them able to catch a wrong field name at all.

### 3. The quests card — `static/app.js`, `static/style.css`

- One builder, `buildQuestsCard()`, returning a `.panel` element or `null` when `S.view.quests` is empty. Two callers, and the same shell in both, so the card cannot drift between the rail and the board.
- **Rail placement (exploring):** in `renderExplorePanel`, *between* the "This area" card and `renderCastCard(panel)` — This area → Quests → Cast a spell. **This is the measured placement, and it replaces the one this bullet originally carried** (appended after the cast card, on the rationale that `#context` should read immediate → actionable → standing reference). That rationale ordered the rail without measuring what the ordering cost, and the cost was the whole card: at the reference viewport — 1440×900, the one `tests/screenshots/conftest.py` fixes — the rail's fixed furniture (viewport, action bar, six party rows) leaves `clientHeight` 848, and on the barrow at quest activation with rail `scrollTop` 0 the card ran **867.5–1010.9**: not one pixel of it on screen, behind a scrollbar this UI deliberately keeps near-invisible. A standing reference nobody can see is not a reference. Ahead of the cast card the same card runs **712.3–855.7** — heading bottom 740.8, quest-name row bottom 768.3, last objective row bottom 843.7 — so every line of its content is visible and only ~8px of the card's bottom padding falls past the fold. "This area" keeps the lead — what is underfoot still comes first.
  - **The price, in the same metric as the finding: the cast card takes the fold.** Measured in the same state, it now runs **867.67–1010.92** against that 848 — not one pixel on screen, its caster select at 904.2–929.2 and its Cast button at 966.2–998.9, both wholly below. Calling that "~155px more distance from the action bar" was the wrong unit for a finding about visibility, and it understated what moved. The trade is accepted deliberately, and it is not symmetric: the quests card is a **standing reference that has to announce itself** — a player who does not know a quest is active will never scroll to find out — while the cast card is a **verb a player goes looking for**, reached by scrolling the rail they already know holds it, and duplicated nowhere else only in the sense that it is the one exploring cast affordance. Something has to be third; the thing that survives being third is the one the player is already hunting for.
  - Residual, measured and recorded rather than fixed here: with a "This area" card above it the quests card starts at 802.7 and its quest-name row bottom is 858.7 — ~11px below the fold. That is not the activation state on this fixture (the barrow's entrance cell carries no feature), so it does not fail the requirement this placement was chosen against, but a document that activates a quest in a keyed room with something underfoot would land there. The fix, if it is ever wanted, is rail furniture — the viewport alone is 380px of it — not card order: putting Quests above "This area" would announce the standing charge ahead of the thing the party is standing on.
  - **Phase 3 inherits this.** Everything above is measured on a *fixture*, because the bundled document carries no quest in this phase — so today a below-the-fold cast card is a barrow-only state. The moment phase 3 authors *The Cold Vein*'s concluding quest, the quests card renders for the default adventure and a cast card past the fold becomes the **normal exploring state of the shipped game** at the reference viewport, for every party with a prepared caster. That makes the rail-furniture question phase 3's to answer rather than a hypothetical: the wireframe viewport is 380px of the ~848, and nothing above the cards has ever been measured against what it costs the cards. A phase 3 planner reading this bullet should treat "should the rail's furniture shrink, collapse, or scroll independently" as an open item their phase surfaces, not as a settled matter phase 2 closed.
- **Town placement:** the first child of `.town-cards` in `renderTownBoard`, ahead of the temple, provisioner, camp, and study cards. Rationale, against the spec's warning that it must never read as an index of the rumors: the rumors are italic serif with a left rule and no shell, the quests card is a bordered `.panel` in a grid of `.panel`s, and the two are separated by the grid boundary. First in the grid puts the charge before the shopping.
- Absent entirely when no quest is active — no heading, no empty state, nothing reserving height. This is the spec's rule and it is also why the bundled document is unaffected in this phase.
- **One card for every active quest, not one card per quest**, headed `<h3>Quests</h3>` — the plural stands whether one quest is active or three, and every other `.panel` in this UI opens with an `<h3>` ("This area", "Cast a spell", "Temple"), which is also most of what keeps the town copy from reading as an index of the rumors above it. Sentence case, per the global UI rule. Rationale for one card: `view.quests` is document-ordered and can hold several — forge documents are not guaranteed to carry one — and N stacked panels would put N borders and N headings in a rail that already scrolls (`.rail` is `overflow-y: auto`, `style.css:105`), for no gain in legibility.
- Contents, per quest, in view order:
  - the quest `name` — `.quest-name`, system sans, semibold;
  - the offer, `narrative`, in `.prose-sm` (the serif referee voice) — rendered only when non-empty;
  - the attribution, `— {speaker}` in `.quest-speaker`, muted sans — only when non-empty;
  - the objectives as a `<ul class="quest-objectives">`, one `<li>` per `ObjectiveView` in engine order: a mono mark (`✓` in `--accent` for `complete`, `○` in `--faint` for `incomplete`) then `objective.name` verbatim. A completed objective's text goes `--muted`; no strikethrough — the chrome stays quiet.
- **A quest whose revealed-objective list is empty renders its name, offer, and speaker with no list at all** — not an empty `<ul>`, and not a placeholder line. A quest authoring every objective `hidden` is legal (`ObjectiveSpec.hidden`), the barrow never produces the state, and a forge document can; the quest is still real and its offer is still the charge.
- Colors come from the existing tokens only. Amber marks a completed objective because amber is this UI's one accent for treasure and accomplishment; there is no new green, and red stays danger-only.
- `objective.name` renders **verbatim**, slug or not, for the same reason work item 2 gives. No prettifying.
- Every authored string reaches the DOM through `textContent`, never `innerHTML` — quest names, offers, speakers, and objective names all come out of an adventure document, and an uploaded document is content the server did not write. (The existing card builders already work this way; the one `innerHTML` in them writes the static `<h3>`.)
- CSS: `.quest-name`, `.quest-speaker`, `.quest-objectives`, `.quest-obj-mark`, added beside the panel rules in `static/style.css`.

### 4. The journal overlay — `static/index.html`, `static/app.js`, `static/style.css`

- Markup mirrors `#map-overlay`, appended after it in `index.html`:

  ```html
  <div id="journal-overlay" class="scrim hidden">
    <div class="overlay-panel journal-panel">
      <div class="overlay-head">
        <span class="oh-title">The journal</span>
        <span class="oh-sub">the party's own record</span>
        <span class="oh-key">J to close</span>
      </div>
      <div id="journal-body" class="journal-body"></div>
    </div>
  </div>
  ```

- **The shared chrome is extracted, not cloned — head and panel both.** `.map-head` and its `.m-title`/`.m-sub`/`.m-key` children become `.overlay-head` / `.oh-title` / `.oh-sub` / `.oh-key`, and the eight shared declarations of `.map-panel` (`style.css:559-568` — width, background, border, radius, shadow, overflow, and the two-property column flex) become `.overlay-panel`. Pinned over the two alternatives: a class literally named `map-head` on the journal panel would be a lie, and cloning either rule set under a second prefix leaves near-identical selectors to keep in step — the same argument twice, so it has to reach the panel as well as the head or it is not an argument.
- **`.map-panel` is deleted outright, not kept as an empty modifier.** The rule at `style.css:559-568` is *exactly* those eight declarations, so extraction leaves nothing behind, and an empty rule kept because the markup still names it is the pattern work item 2 refuses. `grep -rn 'map-panel' static/` returns exactly two hits — `index.html:54` and `style.css:559` — so `index.html:54` becomes `<div class="overlay-panel">` and the rule goes. Between them the two extractions rewrite `index.html:54-58` — the panel's class on 54, and the head's four on 55-58. The journal is the only panel with a modifier: `.journal-panel { max-height: 78vh; }`, which is why its markup above carries **both** classes.
- The element ids (`map-title`) do not change, so `renderAutomap`'s `$("map-title")` (`app.js:1268`) is untouched. `.map-foot` stays as it is — the note editor is the map's alone.
- **Hazard: `.journal-body` needs `min-height: 0` or it will not scroll at all.** `.overlay-panel` carries `display: flex; flex-direction: column; overflow: hidden` and `.journal-panel` adds `max-height: 78vh`, so the body is a column flex item — whose `min-height` resolves to `auto`, meaning its own content height. It therefore cannot shrink below its content: the panel overflows `78vh`, `overflow: hidden` clips it, and every entry past the fold is unreachable with no scrollbar to find. `overflow-y: auto` alone does nothing about it. The map never hit this because it has no `max-height`. The character sheet already did: `.sheet-panel` (`style.css:619`) puts `max-height: 92vh` over the same clipped shell, and its scrolling child `.sheet-body` carries exactly this fix — `min-height: 0` beside `overflow-y: auto` (`:654-658`) — so the sheet is the precisely matching precedent, and proof the hazard is real in this overlay shape rather than a theory. `.rail` (`min-height: 0` with its own `overflow-y: auto`, `style.css:104-105`) and `.stage`/`.log` (`:112-117`, `:449-456`) carry the same fix in two more shapes.
- `renderJournal()` fills `#journal-body` from `S.view.journal`, one `<div class="j-entry">` per entry, in order, each holding:
  - `.j-turn`, mono: `turn ${turnOf(entry.rounds)}` — **a shared helper, not a repeated literal.** This bullet originally prescribed `Math.floor(entry.rounds / 60)` and called it "the same arithmetic as `renderHud`'s clock", which is a convention rather than a guarantee: two copies of a literal stay equal only until someone edits one. `turnOf(rounds)` is the single definition of what a turn is in the client, and both the HUD clock and the journal's stamp call it, so "the stamp and the HUD can never disagree" is a structural claim instead of a hope. Measured on the barrow: the entries written on arrival read `rounds: 60` → "turn 1" — not turn 0, because the stamp is post-travel: `enter_dungeon` charges the town's authored `travel_turns` before the arrival beats land (`exploration.py:1346`; the barrow authors 1). *The Cold Vein* authors 2, so the `adit-draught` line reads turn 2; turn 0 happens only under a document authoring no travel time.
  - `.j-text`, the serif prose voice, via `textContent`.
- Empty state: a single `.j-empty` muted line, "Nothing recorded yet." The overlay always opens; see work item 5 for why the button is never hidden and never disabled.
- CSS home: `.overlay-panel`, `.journal-panel`, `.journal-body`, `.j-entry`, `.j-turn`, `.j-text`, and `.j-empty` all land in the overlay block of `static/style.css`, beside the map's rules they are factored out of.
- Scrolling reuses the two generic helpers `appendLog` already uses on a different element (`logPinnedToBottom`/`scrollLogToBottom`, `app.js:332-344`, both taking the element as a parameter): open pinned to the newest entry, and on a re-render re-pin only if the body was pinned beforehand — so a player reading the top of the record is not yanked to the bottom when a beat lands. No second pair of helpers.
- **The open-time pin runs in `toggleJournal`, after the `hidden` class comes off — not inside `renderJournal`.** On a `display: none` element every scroll metric is `0`, so `logPinnedToBottom` computes `0 - 0 - 0 <= 40` → `true` and a naive render-time pin would re-pin on every re-render whether the player had scrolled away or not. Order matters: unhide, render, then pin.
- `render()` gains `if (JOURNAL.open) renderJournal();` beside the map's clause — and deliberately **no availability check beside it**. The map's `else toggleMap(false)` exists because the map stops being available when the party leaves the dungeon; the journal never stops being available, so the mirror branch would be dead code.

### 5. Entry points, keys, and the overlay guards — `static/index.html`, `static/app.js`

- `<button class="btn ghost" id="btn-journal" type="button">Journal</button>` in `#topbar`'s `.topbar-actions`, before Save. Sentence case; no key chip, because the topbar's existing buttons carry none and the panel head already says "J to close".
- **Always rendered, always enabled, in every mode.** Rationale: hiding it until the journal has content would shift Save and Menu the first time a beat lands — the same reflow the exploring action bar's fixed zones exist to prevent — and the "no disabled ghost" precedent from the library's delete button argues against a disabled state. So the button always works, and an empty journal says so in words.
- `const JOURNAL = { open: false };` beside `const MAP`, and `toggleJournal(force)` in `toggleMap`'s shape: it returns early without `S.view`, toggles the `hidden` class, and renders.
- **The two overlays are mutually exclusive.** Opening the journal closes the map and opening the map closes the journal — both are `.scrim` at `z-index: 20`, and two open at once would stack two panels on one screen. One clause in each toggle.
- Keydown: a `j` branch beside the existing `m` branch, **with no mode gate** — the journal is available in town, in an encounter, in battle, and while exploring, which is the spec's deliberate widening of the map's dungeon-only rule. `m` keeps its `mapAvailable()` gate.
- **`if (MAP.open || S.pacing) return;` becomes `if (MAP.open || JOURNAL.open || S.pacing) return;`.** Without it, `W` walks the party while the journal covers the screen. This is the hazard of the whole item: it is invisible to any click-driven check, because the buttons are behind the scrim and only the keyboard can reach past it.
- Esc chain becomes sheet → journal → map → menu. The journal goes ahead of the map because only one of the two can be open, so their relative order is a formality; what matters is that both sit below the sheet and above the menu, exactly as the map does today.
- **`toggleJournal(false)` joins the existing `toggleMap(false)` in `enterGame` (`app.js:3306`) and `clearGameState` (`app.js:3263`).** This is not a new rule — those two functions already close the sheet and the map at exactly these choke points, and the journal is the third overlay of the same kind. It closes the one route by which a scrim outlives the screen it was opened on: a wipe with the journal up renders the game-over overlay *above* it (`#overlay` is `z-index: 30`, `.scrim` is `20`), and "roll a new party" would otherwise land the fresh session behind a journal nobody opened.
- No change to `showScreen` or `goBack` beyond that. A scrim cannot be *opened* while `#overlay` is up — the topbar buttons beneath it are unclickable and the keydown handler returns early whenever it is visible — so the two choke points above are the whole surface.
- `static/index.html`: `app.js?v=34` → `app.js?v=35`.

### 6. The barrow fixture — `tests/assets/barrow-adventure.json`, `tests/assets/README.md`

- The file is generated once, from the osrlib checkout, and checked in:


- **Generate it after osrlib 1.6.0 is cut** (work item 1). `stamp_document` stamps the library's own version into `engine_version`, so a file generated today would claim `1.5.0`. Nothing compares that field — an adventure envelope is checked, never migrated — but the fixture should not name an engine it was not built from.
- **The recipe is recorded in `tests/assets/README.md`, not in the file.** JSON carries no comments, and that README is already this directory's provenance home. The new section also records *why* a fixture is needed at all: osrlib ships no quest-carrying adventure **document**. Its quest goldens (`phase15_quest.json` and friends) are run dumps — `command_log`, `event_log`, `final_state` — and will not load through `check_document`.
- **That README's opening sentence is corrected in the same edit.** It reads "Fixtures the documentation-screenshot harness loads instead of the bundled adventure", which the barrow falsifies — it is a *test* fixture and the harness must never load it. The directory becomes fixture documents the tests and the harness load in place of the bundled adventure, with the capture-safety material still scoped to the capture document alone.
- What the fixture is, measured by driving it through the real routes: one dungeon `barrow`, one 4×1 level, entrance `(0,0)`, town Threshold, wandering 0-in-6. The quest `the-idol` ("The Votive Idol", speaker Sister Halda) activates on `dungeon_entered`, so the offer is in `view.quests` the moment the party enters. Objective `recover-idol` ("Recover the idol") completes on acquiring `votive_idol` from the `reliquary` cache at `(2,0)`. Objective `speak-the-rite` ("Speak the rite") is authored `hidden` and reveals on entering the crypt at `(3,0)`.
- **No sequence of *player* commands can conclude the quest, which is why this is the right fixture for the phase.** `speak-the-rite` completes on `FlagSetPattern(key="barrow.rite", value="spoken")` (`crawl_fixtures.py:552,628`), and `QuestSpec.completion` defaults to `"all"`, so the idol alone never finishes it. No player command writes a session flag **in this document** — the general rule is narrower than it looks, because `SetFlag` is in `CONSEQUENCE_COMMAND_CLASSES`, so an authored trigger or quest reward writes flags *in response to* player commands. The barrow is safe because its one trigger authors no consequences at all (`crawl_fixtures.py:660-666`, a `narrative` block and nothing else). Phase 3 plans `set_flag` rewards explicitly, so do not carry the unqualified sentence forward. The whole phase-2 drive — `enter_dungeon`, `turn_party`, three `move_party`, `take_treasure` — therefore ends in `exploring`, and cannot land on the client soft-lock the spec documents for `"victory"`.
- **Be precise about what that does *not* say: the endpoint is not restricted to player commands.** `execute_command` parses whatever `parse_command` accepts, which is every referee command — measured, with the idol already taken, a single `{"command_type": "set_flag", "key": "barrow.rite", "value": "spoken"}` over `POST /api/games/{id}/command` completes the quest and puts the session in `victory`. (From a session that has entered the barrow but not yet taken the idol, the same command completes — and thereby reveals — only the hidden objective, and the session stays `exploring`: the `"all"` rule still wants `recover-idol`, and the interpreter checks the rule only at the moment a completion it issued lands, `interpreter.py:411-414`.) That is by design and `AGENTS.md` already leans on it (`award_xp` ~2000 to exercise the level-2 cure flow). The property this phase relies on is about the drive it prescribes, not about a fence the app enforces — so nobody should go looking for one, and firing `set_flag` at the barrow after taking the idol lands on phase 3's unbuilt screen, which is not a bug.
- The new tests load it by monkeypatching `OSR_WEB_ADVENTURE`; the manual drive uses the *appending* `OSR_WEB_ADVENTURES` instead, for the reason the definition of done gives. It is **not** added to the screenshot harness; the capture document stays *The Hollow Tithe*.
