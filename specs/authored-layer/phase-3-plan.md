# Phase 3 plan — endings: victory and the fallen

Implementation plan for phase 3 of [the authored-layer spec](spec.md): both terminal modes end the game like they mean it, and the default adventure can actually be won. Milestone: playing the default adventure end to end — recover the relic, return home, watch the interpreter complete the quest — lands on the victory screen with rewards granted and the journal telling the whole story on the card; a party wiped by a trap lands on the gameover screen the same way. Three things changed since the spec was written. osrlib 1.6.0 is released and is the floor `pyproject.toml` already declares, so this phase needs no dependency work at all — and, measured against the running app, no server-side *code* either: `view.mode`, `view.journal`, `view.quests`, and every purse and valuable the victory screen presents already cross the wire, so the phase is client, content, tests, and docs. Second, phase 2's plan bequeathed this phase an open rail-geometry question the spec never carried — at 1440×900 the exploring rail cannot show three `#context` cards, and the moment this phase authors a quest into *The Cold Vein* that stops being a fixture-only state and becomes the shipped default's normal exploring state — so this plan answers it (work item 3), with measurements. Third, research found one spec gap this plan corrects in `spec.md` on this branch: the victory screen's "same two actions" breaks the README's own veterans promise for the one party that earns it (work item 2 has the argument).

## Spec corrections, made in this PR

The spec's rule is that a phase which finds a spec defect fixes the spec rather than improvising around it. Two amendments, both to the phase 3 section of `spec.md`:

- **The victory screen gains a third, quiet action: Save the party.** The spec pinned "Same two actions (roll a new party into the same adventure; return to the title)", and that pin strands the winning party. The topbar is unreachable under `#overlay` (96% ground, buttons beneath it unclickable) and Esc is the floor on a terminal screen, so a session that has reached `victory` has no UI route to a save — which means the one party that finished an adventure alive, leveled, and rich is the one party the veterans flow can never import. README line 29 promises the opposite ("the veterans of any saved game — they carry their levels, gear, gold, and scars from one module into the next"). The amendment is victory-only by design: a game-over roster imports as corpses (import strips every condition but `dead`), so a save affordance there would offer a party with no future — the fallen's salvage door stays the referee's `PlaceParty`, as the spec already records.
- **The phase 3 roadmap paragraph names the rail-furniture answer as this phase's scope.** The question was raised and measured in `specs/authored-layer/phase-2-plan.md` (work item 3's placement bullets) and explicitly willed to phase 3; the spec's phase list should say so rather than leave phase 3's largest UI decision invisible to a spec reader.

## Scope

In scope:

- The shared terminal-mode constant, and victory routing in `render()` and `boot()`
- The victory screen: the overlay card, its copy, the fortune, the roster, the journal on the card, and the Save the party action
- The rail-furniture answer: the wireframe viewport letterboxes from 4:3 to 16:9, measured
- *The Cold Vein*'s concluding quest, its second bundled item (the captain's day-book), and the document re-stamp
- The capture document's minimal quest, its re-stamp, the `play-view` quest-card assertions, and a seventh README shot: `victory-screen`
- Endpoint pins for the endings against the barrow fixture and the bundled document
- The end-to-end drives: the full default-adventure playthrough to victory, and a solo-party trap wipe to gameover
- The `AGENTS.md`, `README.md`, `content/README.md`, `tests/assets/README.md`, and screenshots-skill sentences this phase falsifies

Out of scope:

- **Narrating the endings, and the `guidance` channel.** Phase 4. With narration on, a homecoming's town arrival may still narrate under the existing beats while the victory overlay stands — phase 4 owns `adventure_completed`'s priority at the top of the `BEATS` table; nothing here touches `server/narration.py`.
- **Any server-code change.** Measured, not assumed: the victory payload was driven end to end on the barrow fixture and everything the screen renders already crosses — `mode: "victory"`, the whole journal, the party's purses and valuables, `adventure_name`, `town_name`. The completed quest correctly *leaves* `view.quests` (measured: `[]` after the ending), which is why the card never tries to read it. `POST /api/games/{id}/save` has no mode gate to add; the engine's `save_game` works in any mode.
- **A save affordance on the gameover screen.** Declined, not deferred — the amendment above has the argument (a dead roster imports as corpses).
- **Restyling the HUD's victory chip.** The spec's "the HUD chip stops reading like a bug" is satisfied structurally: the chip reads "victory" only under a 96%-opaque overlay nobody can see it through. Styling text nobody can see is decoration; the overlay is the fix.
- **Post-victory play, `PlaceParty` salvage UI, campaign continuity.** Engine non-goals mirrored in the spec.
- **Rail changes beyond the viewport letterbox.** The cast card stays a rail card: moving it into the action bar was considered and measured out — the persistent verbs row runs ~395px of the rail's 436 content width and a fifth button would force the ellipsis-shrink the row exists to avoid, and the contextual row wrapping to a second line would break the no-reflow promise (`static/style.css:220-226`). Quests-above-This-area reordering stays declined per phase 2's "what is underfoot still comes first"; the residual states it would fix are recorded in work item 3.
- **Collapsing the quests card's offer prose to save height.** Declined: "the offer reads in the card in the speaker's voice" is phase 2's shipped milestone, and a returning player re-reads the charge there without opening the journal. The height answer is the viewport's to give.

## Work items

### 1. The terminal-mode constant and victory routing — `static/app.js`

- `const TERMINAL_MODES = new Set(["game_over", "victory"]);` beside the `UI` state object, with a comment naming what it mirrors: osrlib's `SessionMode.terminal` (`../osrlib-python/src/osrlib/crawl/commands.py:127-130` — `game_over` and `victory`, exactly). Anywhere the client asks "has this session ended" branches on it; string-matching `game_over` alone is what this item retires.
- `render()`'s mode-driven trigger (`app.js:662`) becomes the two-screen route: `if (TERMINAL_MODES.has(S.view.mode) && UI.screen === "game") showScreen(S.view.mode === "victory" ? "victory" : "gameover");`.
- `boot()`'s guard (`app.js:4191`) becomes `if (!TERMINAL_MODES.has(S.view.mode)) showScreen("game");`. The ordering already does the rest: `boot()` calls `render()` first, `UI.screen` starts as `"game"`, so the render-side trigger routes a restored terminal session to the right overlay before the guard runs — the same path the gameover restore takes today, verified as the soft-lock during research (a barrow session driven to `victory` and reloaded landed on a live-looking screen with zero actions, zero context cards, and the HUD reading "victory"; screenshot in the research record).
- **`enterGame` reorders its tail so the trigger is the single router — the hazard of the whole item.** The two edits above cover page load and live play, but the front door's Continue and the save browser restore through `restoreSave` → `enterGame` (`app.js:3337-3349`, `3436-3457`), and `enterGame` runs `render()` *before* `showScreen("game")` — so during that render `UI.screen` is still `"saves"` or `"title"`, the mode-driven trigger declines to fire, and `showScreen("game")` then lands a restored terminal session on the live game screen with no later render to rescue it (the action bar is empty and the keydown handler returns in a terminal mode — the exact soft-lock this phase kills). Latent today only because no UI route can create a terminal save; work item 2's Save the party makes it live. The fix keeps one routing site rather than adding a second check: `enterGame`'s tail becomes `showScreen("game")` **then** `render()` — synchronous, so no intermediate paint — and the render-side trigger now catches every route into a session: boot, live play, and restore.
- `showScreen` and `goBack` branch on `UI.screen`, not on the mode; the mode-terminal *checks* are exactly the two edited above (measured by grep), and the routes that need them are the three named: boot, live render, restore.
- `goBack()` needs no change: it has no branch for `"gameover"` today and gets none for `"victory"` — an unmatched screen is the floor, which is exactly the Esc-terminal behavior the spec asks for. The keydown comment at `app.js:4213-4215` ("the title and game-over screens are the floor") gains victory. The `UI.screen` comment at `app.js:2793` gains `victory` in its enumeration.

### 2. The victory screen — `static/app.js`, `static/style.css`

The gameover screen's exact mold: its own branch in `showScreen` (`else if (name === "victory") renderVictory(card);` beside `app.js:2816`), rendered into the same `#overlay-card`, Esc-terminal by item 1. The voice is triumph, the accent amber — and amber is already the overlay's accent (`.overlay-eyebrow` is `var(--accent)`), so the screen needs no new color, only new copy and three new blocks.

- **Copy, pinned.** Eyebrow: `the adventure is won` (the mono-caps fact, mirroring gameover's "the tale ends"). Title: `The tale is told` (serif 42px, the story voice — gameover's "Darkness takes the party" is its dark twin). Sub: `` `${esc(S.view.adventure_name)} is done — ${esc(S.view.town_name)} will tell of it for a generation` `` — every adventure document carries a town by contract, so the sentence is safe for any forge document.
- **The fortune.** One line, `.victory-fortune` (mono, `var(--accent)`), between the sub and the roster: `The party carries home {coin} gp in coin and {n} treasures worth {v} gp.` — `treasure` singular when `n` is 1 and numbers formatted with `toLocaleString()` separators, both per the sell card's own conventions (amended at implementation: the template as first pinned would have rendered "1 treasures") — the coin total is `partyGold()` (`app.js:273`, party-wide including the fallen's packs, which is also the engine's own `has_item` reading of who carries what), the valuables count and worth summed over `m.inventory.valuables[].value_gp` exactly as the town sell card does (`app.js:2080-2081`). The valuables clause renders only when `n > 0`; a party with zero coin and zero treasure gets the muted line `The party carries home nothing but the story.` instead — an empty state as a fact, not an apology. Never a per-member breakdown: this is the ending's one sentence, and commerce is over (the spec's "retirement purse" reading — treasure XP already awarded on the homecoming arrival in the same command).
- **The roster.** The staging screen's `.roster`/`.roster-row` grid, reused: `r-name` and `r-class` (`{Class} {level}`) per member, in marching order; a dead member's row takes the existing `.dead` treatment and a `†` before the name (the `rosterLine` convention, `app.js:2831`). No hit points, no ability scores — the fight is over.
- **The actions.** `.overlay-actions` with three buttons: `vt-again` "Roll a new party" (accent), `vt-save` "Save the party" (plain), `vt-door` "Return to the title". The roll-again handler is **extracted, not cloned**: the body of gameover's `ov-again` listener (`app.js:3418-3430` — same adventure, fresh builder, straight to staging) becomes a named `rollNewParty()` both screens wire; two copies of that fallback chain would drift. `vt-save` calls the existing `saveGame()` — it reads only `S.gameId` (which no screen change clears), it toasts above the overlay (`#toast` is z-40 over the overlay's 30), and the transcript line it appends lands behind the overlay, which is harmless. Restoring the save routes back to this same screen through the render-side trigger — which is exactly what item 1's `enterGame` reorder exists to guarantee — and the veterans tab imports the party with the day-book stripped (phase 1's import policy; the item's template is not in the shipped catalogs) — which is the point of the button existing.
- **The journal on the card.** After the actions, headed by a small muted uppercase label (`The journal`), a left-aligned `.victory-journal` block rendering `S.view.journal` in order — the tale, told, readable right there, because `J` is unreachable under `#overlay` (the keydown handler returns for any front-door screen, `app.js:4212`). The entry builder is **extracted from `renderJournal` and shared**: a `buildJournalEntries()` returning the `.j-entry` rows (`.j-turn` stamped via the shared `turnOf()`, `.j-text` via `textContent`) that `renderJournal` fills `#journal-body` with and `renderVictory` appends to the card. The overlay's empty-state line ("Nothing recorded yet.") stays the overlay's alone — a victory card with an empty journal (legal: a forge quest may author no beats) omits the whole block, label included, rather than announcing an absence.
- **Actions above the journal, deliberately.** The exits stay reachable without scrolling a record that grows with the adventure's length; the journal is the coda for the player who wants it. The overlay itself scrolls (`.overlay` is `overflow-y: auto`, `style.css:923`).
- **Hazard: a tall overlay card clips its own top today, and this screen is the first that can get tall.** `.overlay` centers with `align-items: center`; a flex item taller than its scrolling container overflows both ends and the top half becomes unreachable — no existing screen hits it only because none exceeds the ~840px the overlay offers at the reference viewport. The fix is one declaration on the shared card: `.overlay-card { margin: auto; }` — auto margins absorb free space before alignment does, so a short card still centers exactly as today and a tall one pins to the scroll top. Add it to the base rule (`style.css:929`), not a victory-only modifier; every overlay screen inherits the safety.
- **CSS.** `.victory-fortune`, `.victory-journal`, and the journal label class land beside the overlay rules in `static/style.css`, composed from existing tokens only. The `.j-entry` family is already global; no duplication.

### 3. The rail answer: the viewport letterboxes — `static/app.js`, `static/index.html`, `static/style.css`

Phase 2's plan measured the problem and willed it here: at the reference viewport (1440×900) the rail's fixed furniture leaves cards starting at 712 of a `clientHeight` of 848, so the third card is below the fold whichever it is — and the moment this phase authors *The Cold Vein*'s quest, "cast card wholly invisible" becomes the shipped default's normal exploring state. Re-measured on the barrow at quest activation before writing this plan: viewport frame 326px, actions 111, party 228 (head 31 + six 33px rows), three 12px gaps — furniture ends at 700, quests card 712–855 against the 848 fold, cast card 867–1010, wholly off screen. (`AGENTS.md`'s "the wireframe viewport alone is 380px" was miscounted; the true figure is 326, and the rewrite in work item 8 corrects it.)

- **The decision: the viewport gives its letterbox — 4:3 becomes 16:9, an 81px yield, and nothing else moves.** Prototyped live before pinning (a centered 16:9 crop applied in-page on the barrow, both dark and torchlit corridor states, screenshots in the research record): the crop is a strict improvement, not a compromise. The wireframe's information — walls, doors, the vanishing point — lives in the horizon band; what the 4:3 frame spends its extra 81px on is blank near-floor and near-ceiling fill. The 16:9 frame reads tighter and keeps the "small, honest window" exactly as settled. Measured effect at the reference viewport: furniture ends at 619, the barrow's quests card runs 631–774 — **fully visible** — and the cast card's heading and caster select crest the fold (786–848), announcing the verb.
- **Mechanics.** Three coordinated edits, all named: `static/index.html`'s canvas attributes `width="920" height="518"` (920 × 9⁄16 = 517.5; 518 is the nearest integer); `static/style.css`'s `.viewport-frame` gains `aspect-ratio: 920 / 518` in place of `4 / 3`; `static/app.js`'s `VP` becomes `{ W: 920, H: 518 }`.
- **Hazard: the focal length is tied to the height it must stop being tied to.** `drawScene` computes `const f = VP.H * 1.05` (`app.js:965`) — shrink `VP.H` naively and every wall narrows too: the change becomes a zoom-out, not a crop. The edit is `const f = VP.W * 0.7875;` with a comment saying why it is anchored to width — 920 × 0.7875 = 724.5, byte-identical to today's value, so at the new height the scene is a pure vertical crop with the horizon centered (`cy = VP.H / 2` is already right). Changing the multiplier is the zoom knob; changing `VP.H` is the letterbox knob; the comment keeps the two from being confused again.
- **`drawGateScene` survives the crop without edits — verified by arithmetic, confirm visually at implementation.** Its layout is proportional (`horizon = VP.H * 0.66` → 342) except the dome's fixed `horizon - 260` (`app.js:1171`), which lands at y = 82, comfortably inside the 518 frame. The stars scatter over `horizon * 0.82` and scale with it. One fringe case to eyeball rather than trust: the glow rect anchored at `horizon - 390` (`app.js:1186`) now tops out above the frame, so the radial glow's faint outer edge meets the top border instead of fading out inside it — cosmetic at alpha ≈ 0.05, and the constants are the place to tune if the hold looks squat or the glow looks cut.
- **Residuals, measured and recorded rather than fixed.** *The Cold Vein*'s card is taller than the barrow's (two objectives, a longer offer): projected ~175px, it still fits whole in the featureless corridor state (631–806) with the cast heading visible below it, **provided the authored offer stays within two rendered lines** — an authoring constraint work item 4 carries. On a featured cell ("This area" above it, ~90px for a one-feature cache), the quests card's name, offer, speaker, and first objective are on screen and its tail is not; that state is transient (the player is standing on something they are about to act on), the announcement holds, and the fix if it ever matters is phase 2's recorded alternative (Quests above This-area), declined here for the same "underfoot comes first" reason phase 2 gave. (Amended at implementation, measured on the shipped default at the crib cache: the This-area card is 99.4px and the Cold Vein card taller than projected, so what stays on screen is the heading, the name, and the whole two-line offer — offer bottom 846.1 against the 848 fold — while the speaker and objectives go under. The announcement still holds; the transient-state argument is unchanged.) Battle collects the same 81px for the declaration panel and group chips, free.
- **What this moves elsewhere:** four README shots re-frame (the letterbox is in `play-view`, `character-sheet`, `automap`, and `combat-round`), covered by work item 7's full recapture; the `AGENTS.md` rail-measurement sentences are rewritten with post-change measurements taken at implementation time (work item 8), not with this plan's projections.

### 4. The Cold Vein's concluding quest and the day-book — `content/adventure.json`, `content/README.md`

The document's own hooks already seed the ending: hook 1 has the headman staking anyone willing to prove the vein and paying "twice over for the mine captain's day-book", and hook 4 has the captain's record stopping halfway across a page. The quest collects the promise the hooks have been making since phase 1.

- **The item.** `captains-day-book` — a `gear` template in `payload.items` beside `verrow-token`, `cost_gp: 0` (the found-not-bought convention `content/README.md` records), display name "the captain's day-book". Original work, like everything else in the file.
- **The placement.** A new authored cache in level 2, area 18 ("The cold face" — the climax, where hook 4 says the writing stopped), carrying the day-book in its `item_ids`. The two zombies keyed there guard it; the area's generated type-C treasure coexists with the authored cache exactly as areas already mix features. The relic is therefore behind the climax fight but never behind a locked door or a gate — the route rule the guide already enforces.
- **The quest.** `payload.quests` gains its first entry:
  - `id: "the-day-book"`, `name` "The Captain's Day-Book", `concludes_adventure: true`, `completion: "all"`.
  - `activation`: `dungeon_entered` on `cold-vein` — the charge lands the moment the party first steps into the mine, the barrow fixture's own pattern. There is no event channel before the first command, so an activation-less quest would surface silently (the spec's warning); this one announces itself in the transcript and the journal at the adit mouth, beside `adit-draught`.
  - Objective 1: `id: "recover-day-book"`, `name` "Recover the captain's day-book", `when` an `item_acquired` clause on `captains-day-book`, an authored `progress` beat. The acquisition spine is the anti-short-circuit: an imported or carried-in copy of the item satisfies `has_item` but never *fires* `item_acquired` in this session — and belt over braces, phase 1's import policy strips the non-shipped template on the way in anyway.
  - Objective 2: `id: "bring-it-home"`, `name` "Bring it home to Cinderhope", `when` a `town_entered` clause with a `has_item` condition on `captains-day-book` (`consumes` absent — a quest clause condition may never consume; the engine rejects the toll form at parse), an authored `progress` beat.
  - Both objectives are visible (no `hidden`, no `reveal_when`), and both author `progress` only — an unhidden objective's `offer` beat rides a reveal that never fires (`ObjectiveSpec`'s own contract), so authoring one would be dead weight. The consequence, recorded as deliberate: `objective_revealed` never fires in the shipped document; the reveal surface stays exercised by the barrow fixture in `tests/test_quest_log.py`.
  - `narrative`: an authored `offer` (the headman's charge, in his voice — **two rendered card lines at most**, the height budget work item 3 measured), an authored `completion` beat, and a `speaker`. The speaker is the headman of Cinderhope; naming him is the implementation's authoring work under the file's original-work rule.
  - `rewards`, in authored order: `grant_coins` to `@party` with `{gp: 100}` (the interpreter expands `@party` per living member — the payment is per head, which is how "pay twice over" reads at the table), then `award_xp` to `@party`, `amount: 200`. Both are terminal-legal; a reward-triggered level-up's events landing after the ending event is expected and tolerated (spec finding). `set_flag` is declined: `narrate.py::_on_flag_set` renders nothing and no later content reads a flag, so it would be invisible wiring.
- **The stamp.** `engine_version` moves `"1.5.0"` → `"1.6.0"`: the document now authors `ObjectiveSpec.name`, a field 1.5.0 does not know — a 1.5.0 engine would load the file and silently strip the names to slugs rather than refuse, and the stamp should name the engine the document is actually written for. `schema_version: 3` stands.
- **What the quest does not disturb, verified at implementation.** Activation on `enter_dungeon` adds transcript and journal lines but draws no dice and costs no time (`ActivateQuest` is bookkeeping), so the documented scripted route to the first fight — three moves, the odometer arithmetic, the kobolds — is mechanically unmoved; the existing bundled-document tests and `tests/test_battle_round.py` must pass unchanged. Sweep the suite for any assertion that the bundled document carries no quest (phase 2 scoped those to the barrow precisely so this phase would not trip them, but verify rather than trust).
- **`content/README.md`, same PR:** the stamp paragraph (1.6.0 and why), the feature-index table (concluding quest, second bundled item, the new cache at the cold face), the authored-layer section (the quest's shape, the per-head reward reading, the deliberate `objective_revealed` absence), the deterministic-route section (the two activation lines now in the `enter_dungeon` response), and the retirement of "payload.quests is absent — the concluding quest arrives with the endings work".
