# Phase 4 plan — the narrator learns the authored layer

Implementation plan for phase 4 of [the authored-layer spec](spec.md): LLM narration catches up with the authored beats and the `guidance` steering channel, and `specs/llm-narrative/spec.md` is amended in the same PR to name that channel as the one deliberate exception to its player-safe-prompts principle. Milestone: with the narrator on, entering a guided level colors the passage the way the author steered it; a run in which the phase-1 trigger fires carries that trigger's steering and no other's; completing the adventure yields a closing passage that keeps the authored completion line's words and facts intact. Two things changed since the spec was written. Phase 3 landed the concluding quest and the victory screen, so every collision this plan researched — the activation beside the adit trigger, the reward coins beside the ending — was measured against shipped content, not projections. And research found two engine gaps this plan files rather than works around: `GrantCoins` emits a bare `ItemAcquiredEvent` indistinguishable from a treasure share (`../osrlib-python/src/osrlib/crawl/session.py` `_handle_grant_coins` — no source, no marker; the `Event` base carries only `code` and `visibility`), and a gated transition's success beat rides an arrival event that names where the party arrived and nothing about the crossing it took (`crawl/events.py`, `LocationEnteredEvent`), so the spec's "door or transition spec" gate mapping is honest for doors only. The second gap falsifies one spec sentence, corrected below.

## Spec corrections, made in this PR

The spec's rule is that a phase which finds a spec defect fixes the spec rather than improvising around it. One amendment to the phase 4 section of `spec.md`, plus the `specs/llm-narrative/spec.md` amendment the spec itself orders:

- **The gate-guidance mapping is door-only, and the spec sentence saying "door or transition" is corrected.** `DoorEvent` carries the party's cell and the command's direction (`crawl/exploration.py`, `_handle_open_door` — `x, y = _position(session)`), and `LevelSpec.edge()` resolves the same edge from either side, so a door gate maps back honestly. A gated transition's success beat rides the arrival's `LocationEnteredEvent`, which carries `location_kind`/`location_id`/`level_number`/`dungeon_id`/`narrative` and nothing naming the transition taken or the departure cell — the only "mapping" available is a reverse search over the document's transitions filtered by destination and tie-broken by comparing authored success text against the event's `narrative`, which is the answer-second-guessing anti-pattern this effort has now documented three times (`_consumed_item_phrase`, the trap bearing, the objective labels). The correction narrows the spec's sentence to the door form and names the engine issue for the transition form. The bundled gate is a door (a phase-1 decision made for an adjacent reason: same-level transitions drop their beats), so the shipped document loses nothing.
- **`specs/llm-narrative/spec.md` is amended as the authored-layer spec directs**: design principle 2, the prompt-design section, and the "prompts contain only player-visible material" acceptance criterion are rewritten to name the guidance channel as the one deliberate exception — plus the goals bullet that makes the same absolute claim in one line, corrected for the same reason. The exact text lands on this plan's branch; the beats *table* in that spec is deliberately left alone (see out of scope).

## Scope

In scope:

- Four new rows in `BEATS` — `adventure_completed`, `quest_completed`, `objective_completed`, `quest_activated` — each an emphasis that is a tone plus a limit, with the priority order pinned and tested
- The guidance channel: `build_prompt`'s single keyword-only `guidance` parameter, the never-quote block, assembly in `observe` from the four carriers, per-snapshot guidance with the coalescing merge rule
- Authored `guidance` for *The Cold Vein*: both levels' ambient slots, the quest's block, the gate's, and the trigger's — with `content/README.md` updated in the same PR
- Tests in `tests/test_narration.py`'s established shapes, the structural strings-only test's comment rewritten, and guidance-value sweeps added to `tests/test_authored_layer.py`'s wire tests
- The `specs/llm-narrative/spec.md` amendment (this PR), and the `AGENTS.md` sentences the implementation falsifies (implementation PR)
- Two osrlib issues filed engine-first (grant provenance; the transition crossing), before any workaround would otherwise be written

Out of scope:

- **Narrating gate refusals.** Settled by the spec: a refused gate emits no events, `observe` receives an empty delta and returns, and the authored refusal already renders verbatim in the transcript. Prose there would be new pipeline design to spec on its own.
- **Re-wording the `grant_coins` reward line in `narrate.py`.** Declined, engine-first. The candidate: the quest's per-head payment currently renders through the haul collapse as a treasure split — the interpreter expands `@party` to one `GrantCoins` per living member, each emitting a bare `ItemAcquiredEvent` with `coins_gp_value`, and the adjacent coin acquisitions are exactly what `_is_distribution` collapses, so a three-survivor homecoming reads "The party splits 300 gp in coin." Truthful in sum, wrong in frame — it reads as a pot split, not the headman counting out the price per head. But the event is byte-identical in shape to a `TakeTreasure` share: no `source` stamp (commands carry `source`; events don't), no grant marker, same code `exploration.item.acquired`. Every honest discriminator is session-side or mode-side, and a mode test at render time would re-word every *historical* haul on a whole-log re-render — the `_area` defect again. The fix is the engine stamping provenance on the event (or carrying the issuing command's `source`); the issue is filed in the definition of done and the wording follows in a later change once the engine states the fact. No `narrate.py` edit ships in this phase — which also means the deterministic transcript is byte-identical and **no README screenshot moves** (the capture run's `victory-screen` card shows the journal, whose authored beats are untouched, and the transcript behind the 96%-opaque overlay is invisible regardless).
- **Transition-gate guidance.** Declined pending the engine naming the crossing (issue filed; spec corrected above). No reverse search over `transitions` gets built.
- **A `gate_passed` beat.** Declined: a door opening is not a moment worth prose on its own — the authored success line already renders verbatim in the prose voice. The recorded consequence: since guidance only reaches a prompt when a beat fires, a gate's steering reaches a live prompt only when its success run *also* carries a beat (a trapped gated door, a gated door into a first-visit area — not this document's wicket, which coincides with nothing). The carrier is still plumbed and pinned by tests at the assembly seam; steering, not script, and the window is the spec's own.
- **An `objective_revealed` beat.** Declined: the spec charters three beats and leaves only `objective_completed` to this plan. A reveal's authored offer already renders verbatim in the transcript and the journal, the default document authors no hidden objective (reveals are the barrow fixture's surface), and a revealed objective's `guidance` starts riding its quest's block the moment it reveals — the steering arrives without a beat.
- **Any client work.** Recorded as none, measured: the poll loop is screen-agnostic (`absorb` → `maybePollNarration` in `static/app.js`), so the closing passage generates, appends behind the victory overlay, and interleaves on reload — the exact position the existing `game_over` beat has always had behind the gameover overlay. The winning player reads the journal on the card; the passage is archival. Putting the passage on the victory card would need the card to poll and a new surface decision — future work if ever wanted, not a forgotten wire. No `app.js` edit, no `?v=` bump.
- **Rewriting the llm-narrative spec's beats table.** Declined: that spec pins `BEATS` in code as the data home ("tuning is an edit, not a refactor"), and the table there documents v1 — `leveled_up` already post-dates it without an edit. The amendment touches only the player-safety claims the guidance channel actually changes.
- **Guidance persistence, SSE, or any wire change.** Guidance is prompt-side only; `state()`, `tail()`, the poll endpoint, and the reload interleave are untouched. Nothing new crosses the wire, under any flag.
- **Regenerating the barrow fixture with guidance.** The bundled document exercises every carrier; the fixture keeps proving the reveal surface and the wiring sweeps it already owns.

### 1. The four new beats — `server/narration.py`, `tests/test_narration.py`

- Four matchers in the shape of the existing ones, each on `event_type` alone: `_adventure_completed`, `_quest_completed`, `_objective_completed`, `_quest_activated`. All four ignore `in_dungeon` (the ending and the homecoming objective land in town; an offer can arrive anywhere).
- **The table order, pinned in full** (new rows starred):

  1. `adventure_completed` *
  2. `area_entered`
  3. `encounter_started`
  4. `battle_ended`
  5. `member_died`
  6. `quest_completed` *
  7. `objective_completed` *
  8. `leveled_up`
  9. `trap_sprung`
  10. `quest_activated` *
  11. `treasure_found`
  12. `game_over`

- **`adventure_completed` at the very top**, above `area_entered` — the spec's own pin, with the reason in a comment: the ending's run also carries the quest completion (always — the engine emits the two back to back), the homecoming's treasure-XP award, the reward coins, and possibly a reward-triggered `leveled_up`; none of those may out-prioritize the ending. One consequence worth stating: a forge quest that concludes on a first-visit `area_entered` puts module prose in an ending run, the `rule.name == "area_entered"` branch in `observe` doesn't run, no `replace_id` is stamped, and the raw module prose renders immediately with the closing passage appended after — the same fail-open surface as a dropped generation, accepted deliberately because replacement is coupled to the `area_entered` rule winning.
- **`area_entered` stays above the quest beats — the bundled `enter_dungeon` collision, decided.** The first entry into the mine lands `quest_activated` (`the-day-book` activates on `dungeon_entered`), the `adit-draught` journal line, *and* the first-visit adit prose in one command. `area_entered` wins: replacement mode is structural (the client holds the marked prose behind a placeholder awaiting the passage), and letting `quest_activated` outrank it would break replacement in exactly the showcase moment — raw prose rendering while the passage narrates paperwork. The loser's material is not lost: `just_now` is the whole delta's rendered entries, so the "New quest:" line, the offer, and the journal line are all in the prompt as facts — and the quest is *active* by snapshot time, so its `guidance` steers the same prompt through the channel (work item 2). This is the settled pattern: at most one beat fires and the others' entries ride the prompt.
- **`quest_completed` below `member_died`, above `leveled_up`** — the elegy-over-celebration rule the table already carries for `leveled_up`, and the same out-prioritizing argument in miniature: a non-concluding quest's `award_xp` reward can level a member in the completing run, and the level-up is the completion's side effect, not the story.
- **`objective_completed` is a beat — the call the spec left to this plan, taken yes**, directly below `quest_completed`. The rationale, researched against the bundled document: objective 1 completes when the day-book comes off the captains-board cache, in the same delta as a `treasure_found`-worthy haul — and the moment's meaning is *the party found the thing it came for*, not the shine of the cache beside it. An objective completion above `treasure_found` gives the fetch its due; the haul's line rides `just_now` as facts. Objective 2 completes in the ending's run, where rows 1 and 6 outrank it — correct, the ending is the story there. The queue coalesces and objectives are rare (they are authored, not rolled), so the cost argument that keeps movement and searches out of the table doesn't bite.
- **`quest_activated` below `trap_sprung`, above `treasure_found`**: sudden violence in the same delta (a trapped threshold that wakes a quest) reads as the trap, with the offer verbatim in the transcript and the prompt; but a quest waking on an *acquisition* is that acquisition's meaning, so it outranks the loot.
- **Emphasis strings, pinned exactly** — each a tone plus a limit, sharing the limit token "word for word" so one test can hold all four to the sibling standard:
  - `adventure_completed`: "The adventure ends in triumph — close the whole tale. Any authored ending has already been read to the table word for word: never restate or rephrase it. Keep every name, payment, and fact exactly as stated, and invent no epilogue the facts do not carry."
  - `quest_completed`: "A quest is done; give the moment its weight. Any authored completion line has already been told word for word: never restate or rephrase it — put the prose around it, and claim no reward the facts do not name."
  - `objective_completed`: "The story advances a step; mark what was just accomplished. Keep the objective and its quest exactly as named. Any authored progress line has already been told word for word: weave around it, never over it."
  - `quest_activated`: "A charge is laid on the party — give the moment the weight of an errand accepted, in the voice the facts give it. Any authored offer has already been delivered word for word: never repeat or reword it, and name no speaker, promise, price, or condition the facts do not state."

  "Any authored" is deliberate: `narrative` is `None` on every one of these events when unauthored (verified on all four models), and an emphasis asserting a line that isn't there would be the trap-beat defect inverted. The `quest_activated` emphasis names no speaker for the same reason, found in review: `QuestActivatedEvent` carries none and the transcript renders the offer unattributed (`_on_quest_activated` — the authored `speaker` reaches the player on the quests card, never the prompt's facts), so at activation a speaker's name can sit in the guidance block alone, and an emphasis inviting "the speaker's voice" would ask the model to state steering as fact. The verbatim discipline lives here and in the transcript — `build_prompt` learns nothing about beats (the standing rule: fix truthfulness in the transcript, never by widening the builder).
- Tests, in `TestDetectBeat`'s idiom (SimpleNamespace events, `entry()` helpers): one detection test per new rule, and the priority pairs — `test_adventure_completed_outranks_its_own_quest_completion` (the always-together pair), `test_adventure_completed_outranks_the_reward_level_up` (spec-named), `test_the_ending_outranks_a_first_visit_area` (with `module_prose` present and a comment on the raw-prose consequence), `test_a_first_visit_area_outranks_the_activation` (decision above, the bundled enter-shape: `module_prose` + `quest_activated` event), `test_member_death_outranks_the_quest_completion`, `test_quest_completed_outranks_the_reward_level_up`, `test_objective_completed_outranks_the_haul_beneath_it`, `test_the_activation_outranks_the_loot_it_rode_in_on`. Plus one emphasis test in `TestTrapEmphasis`'s mold asserting all four new emphases carry "word for word" and the siblings keep their constraints.

### 2. The guidance channel — `server/narration.py`, `tests/test_narration.py`

The one steering channel, assembled in `observe`, carried per-snapshot, rendered by `build_prompt` as a marked block. `server/app.py` is deliberately untouched: `observe(session, events, entries)` already receives the raw delta — referee events included (the command path passes `session.event_log[mark:]` unfiltered; `observe` builds its own `visible` list for detection) — so the channel needs no new plumbing at either call site.

- **`build_prompt` gains `guidance: str = ""`**, keyword-only like every other parameter, annotated `str` so the structural strings-only test passes by its letter. Default `""` is load-bearing: an empty channel renders nothing, so an adventure authoring no guidance produces prompts byte-identical to today's — a property one test pins. The block renders after the `JUST NOW` moments and before the final "Narrate this moment." line (nearest the instruction, where a small local model actually obeys it), under a module constant so tests assert the real string:

  ```python
  GUIDANCE_HEADER = (
      "REFEREE GUIDANCE (private steering — never quote it, never reveal it, "
      "never state it as fact):"
  )
  ```

  When `guidance` is non-empty: append `GUIDANCE_HEADER`, then the guidance text. The marking lives entirely in the block, not in `SYSTEM_PROMPT` — one named channel in one place is what keeps "never crosses the wire, never prints as written" auditable at one seam, which is the spec's own argument against scattering.
- **`BeatSnapshot` gains `guidance: tuple[str, ...] = ()`** — the carrier blocks of that beat's run, in assembly order, one string per block. A tuple rather than a pre-joined string because dedup under coalescing is block-granular. The default keeps the test helper `snapshot()` and every existing construction site valid.
- **The worker merge**: when the batch drains, concatenate the snapshots' guidance tuples oldest-first (the same order the `JUST NOW` moments already take), dedup exact strings keeping the first occurrence, join with `"\n"`, and pass the result as `build_prompt(..., guidance=...)`. A coalesced trigger's steering is neither dropped nor carried past its window: it rides its own snapshot into the merged prompt, exactly once.
- **`assemble_guidance(session, events) -> tuple[str, ...]`** — a module function beside `location_line`, called from `observe` *after* the `rule is None` early return (no work on beat-less commands; the `self.enabled` check already precedes). Empty and unauthored blocks (`""`, `narrative is None`) are filtered everywhere. Assembly order within one snapshot, pinned as ambient-to-specific — the place, the standing charge, the thing that just happened: level → quests (each quest's block then its riding objectives', quests in document order, objectives in authored order) → triggers (in event order in the run) → gate.
  - **Level**: `session.dungeon_state.location`; when `kind == "dungeon"`, `session.adventure.dungeon(location.dungeon_id).level(location.level_number).guidance`, with `location_line`'s exact `try/except ValueError` posture. In town: no level block. The occupied level is the post-command one, which is the honest reading of "while occupied" — the same read `location_line` has always made.
  - **Quests and objectives — the window rule, pinned.** osrlib's window for a quest is *while active*. Live state at snapshot time is post-command, so the one edge where a state read and the events' own moment disagree is the completing run — and the engine's own matching stance is that events are judged by the moment they describe, never by current state. So the rule: **a carrier steers every run from the one that brings it into play through the one that takes it out, both inclusive.** Concretely: include a quest's block when `session.quests[quest.id].status == "active"` *or* a `quest_completed` event with its id is in the run; include an objective's block (riding its quest) when its state is `revealed and not complete` *or* an `objective_completed` event with its ids is in the run. The activation edge needs no special case — the activating run's post-command status is already `active`. This is also what puts the concluding quest's steering into the closing passage's prompt, where the author would expect it. Note the status literal is `"completed"`, not `"complete"` (`crawl/session.py`, `QuestState` — `inactive`/`active`/`completed`); objective state has `revealed`/`complete`, and a visible-from-birth objective is born `revealed=True`.
  - **Triggers**: for each `trigger_fired` event in the raw delta (referee-visible, inspected server-side and only here), find the spec by id — `next((t for t in session.adventure.triggers if t.id == event.trigger_id), None)` — and take its block's guidance. There is no `Adventure.trigger(id)` accessor (only `dungeon()` and `quest()`); a linear scan of a frozen content tuple matches the engine's own style and needs no engine change. The window is exactly the firing run, delta-scoped by the event itself.
  - **The gate — door form only, with a relocation guard.** When the delta carries a `DoorEvent` whose `narrative` is set (a gate's success beat rides only there, and only when authored), *and the delta carries no `location_entered` event*, resolve `session.adventure.dungeon(...).level(...)` from the session's location, then `level.edge((event.x, event.y), Direction(event.direction))` — the event carries the party's cell and the command's direction, and `LevelSpec.edge` canonicalizes, so either side of the edge resolves the same entry — and take `edge.door.requires.narrative.guidance` when the whole chain is authored. The guard is the honesty argument: no trigger pattern matches a `DoorEvent` or `ItemConsumedEvent` (the pattern union is location/item/monster/flag — verified against `crawl/triggers.py`), so an open/force command cannot relocate the party *except* through a door-trap's transition effect — which emits `location_entered`, which the guard catches, dropping the gate block rather than resolving the edge against the wrong level. A missed lookup at any step yields no block, never a fallback. The transition form is declined and filed (spec correction above).
- **`observe` wiring**: `guidance=assemble_guidance(session, events)` on the snapshot; nothing else in `observe` moves — the replacement branch, the `_recent` buffer, the anchor, all untouched.
- **The structural strings-only test keeps passing by its letter, and its comment is rewritten** to say what it now proves: no session or event objects reach the builder — the steering channel included, which enters as a plain string assembled by `observe`, the one place allowed to read the document.
- Tests, in the file's established idioms (`FakeProvider` + `threading.Event`; `snapshot()` gains a `guidance=()` parameter):
  - `TestBuildPrompt`: the block renders under `GUIDANCE_HEADER` before the closing instruction; `guidance=""` produces a prompt byte-identical to one built without the parameter (the unauthored-document property).
  - `TestNarrationEngine`: `test_coalescing_merges_guidance_in_beat_order_and_dedupes` — two snapshots sharing one block and carrying one each; the recorded prompt holds the three distinct blocks, oldest snapshot's first, the shared block once.
  - `test_nothing_in_the_channel_crosses_the_wire`: with guidance-carrying snapshots processed, `json.dumps` of `engine.state()` and `engine.tail(0)` carries no guidance text (the canned provider proves the surfaces, not the model).
  - The observe-level and window tests live in work item 4, against the shipped document, once work item 3 has authored the strings they read.
