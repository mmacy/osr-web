# API surface

The wire contract in `AGENTS.md` governs everything here: only the player projection crosses the wire, and adding a response field means asking first whether it leaks referee state.

- `GET /api/adventures`: the library, as `{adventures: [{id, name, description, hooks, town_name, dungeon_count, removable, source_kind}], default_id}`. The middle extras are the browsing pane's player-safe facts (hooks, the town's name, the count of enterable dungeons), read off each document's own cover so the library can be browsed with no game session behind it. The last two describe the entry's place on the server's disk, never a path. `removable` is whether `DELETE` would take it. `source_kind` is which of `bundled`, `external` (reached through `OSR_WEB_ADVENTURES`), `file`, `folder`, or `link` it is. The client names the last three in the delete confirmation, because unlinking a symlink to an osr-forge output directory and deleting a dropped folder are different acts.
- `POST /api/adventures`: add a browsed adventure JSON to the library. The body is the stamped document itself, the file's bytes rather than a wrapper object. The client sends `file.text()` raw so the server vets, dedupes, and writes exactly what the player picked. The server validates the envelope (`check_document`) and the payload (`Adventure.model_validate`) before writing into `library.adventures_dir()`, so `OSR_WEB_ADVENTURES_DIR` redirects uploads too. For a document the library already contains byte-for-byte, the endpoint returns the existing entry and writes nothing. Invalid content is a 422 with a friendly `detail`. Returns `{adventure_id, adventures, default_id}`: the new entry's id plus the same refreshed listing as the GET.
- `DELETE /api/adventures/{adventure_id}`: delete an adventure the drop directory holds. Only the drop directory is ever written to. An entry whose `removable` is false (the bundled document, anything from `OSR_WEB_ADVENTURES`) is a 422 with a friendly `detail`, and unknown ids are 404. What goes is the drop directory's own item, the `.json` file or the directory containing it. `server.library.remove_adventure` unlinks a symlink without touching the osr-forge directory it points at, and removes a real dropped folder with everything in it. Returns `{adventure_id, deleted, adventures, default_id}`, the same refreshed listing as the GET, because deleting one entry can renumber a name-slug collision (`foo-2` becomes `foo`). A game already under way is unaffected: the server keeps its document in memory and a save contains its own copy. Tests: `tests/test_library_delete.py`.
- `GET /api/saves`: player-safe save summaries. Each has `save_id`, `name` (the player's own, or derived server-side as "{adventure} — level N, turn T"), `adventure_name`, `saved_at` (mtime), `turn`, `place` ("Cinderhope" or "The Cold Vein, level 2"), and the roster with `dead` flags. Never the save document itself. `tests/test_saves.py` pins the exact key set.
- `PATCH /api/saves/{save_id}`: body `{name}` renames a save (stripped, ≤60 chars, empty is a 422). The name is stored as an extra top-level key on the save file, which the document envelope ignores by contract. The file's mtime is preserved so the list order holds. Unknown ids are 404.
- `DELETE /api/saves/{save_id}`: deletes the save file. Unknown ids are 404. Ids are fenced to plain filename stems, so anything path-shaped is a 404.
- `DELETE /api/saves`: deletes every save the listing shows, and nothing else in the directory (`*.json` only). Returns `{deleted, saves}`: the count removed plus the summaries as they stand afterwards, so a file the server could not delete stays visible to the client instead of vanishing from a screen rendered as if every delete had succeeded.
- `GET /api/creation/catalog`: rulebook data for the creation wizard. It has the classes (requirements, primes, armour/weapon policies), level-1 arcane spells, choosable languages, alignments, the equipment list, the `ability_methods` (`3d6`, `4d6_drop_lowest`), and the curated equipment `kits` (one per class, each tagged with its `class_id`).
- `POST /api/party-builders`: open a roll-your-own party builder. Optional body `{house_rules: {ability_method, max_hp}, seed, premade}`. The house rules set the table rules up front. The optional `seed` makes the builder's own draws reproducible: the same seed plus the same step sequence rolls the same abilities, hit points, and gold. The seed is builder-scoped and write-only. It is never echoed in a payload and is never a game's master seed. Anything but an integer in `[0, 2**128)` is a 422, and when it is omitted, the builder draws fresh randomness. `premade: true` fills the builder with the pregenerated six on creation. That is the staging screen's party, held with **no game session** until `POST /api/games {party_builder_id}` commits. `GET /api/party-builders/{id}` returns its roster, `house_rules`, and draft state.
- `POST /api/party-builders/{id}/step`: one creation step. Body `{action, ...params}` with actions `house_rules` (`ability_method`, `max_hp`, locked once the first character is rolled), `roll_abilities`, `choose_class`, `adjust`, `choose_spells`, `choose_languages`, `roll_hit_points`, `roll_gold`, `buy`, `buy_kit` (`kit_id`, only the draft's own class's kit, all-or-nothing against the purse), `return`, `finalize`, `discard`, `remove_member`, `premade`, and `rename` (`index`, `name`, a finished member's inline rename). `premade` rerolls the whole premade set, optionally under new `ability_method`/`max_hp`. The house-rules lock doesn't apply to it, because no rolled member survives, and the builder rejects it while a hand-rolled draft is in progress. A broken rule is a 200 with `accepted: false` and friendly `rejections`. Every response includes the full builder state.
- `POST /api/games`: body `{seed?, adventure_id?, party_save_id?, party_builder_id?, house_rules?}` for a new game, or `{save_id}` to restore a full session. For a new game, the default adventure is used when `adventure_id` is omitted. The party is imported from that save when `party_save_id` is set, or taken from the builder when `party_builder_id` is set, which consumes the builder. `house_rules` `{ability_method, max_hp}` bends the pregenerated party's creation draws and is ignored when a party is imported. Returns `game_id`, `view`, `cell`, `sheets`, `spellbook`, `spell_books`, `learnable`, `temple_services`, `hooks`, `dungeons`, `log`. `temple_services` is the temple's posted price list: the engine's `HEALING_SERVICES` table as `[{id, name, cost_gp}]`, rulebook-public. `sheets` entries also include `spell_slots` (the member's own progression row, where `spell_slots[i]` is slots at spell level `i + 1`, empty for non-casters), `rested` (a night's sleep is banked and unspent on preparation), `level_title` (the class table's title at the member's level, `null` past the printed list), and `spell_picks` (per-spell-level open spell-book slots, the row's capacity minus the spells the book contains, same index convention as `spell_slots`, empty for everyone but arcane casters). `spell_books` is each member's *preparable* list: an arcane caster's own spell book, or a divine caster's class spell list truncated to the levels their row has slots for. It is omitted when empty, so a level-1 cleric has no list. `learnable` maps each member with an open spell pick to the `[{id, name, level, intro}]` candidates their book has room for: the class spell list at each open level minus the spells already held, sorted by (level, name). Members with no open pick are absent. `spellbook` entries include `level` beside `name`/`mode`/`target` and cover every preparable spell, not just memorized ones. `cell.features` entries include `trap_found` and `inspected_by`. `trap_found` is true only after the party's own successful inspect, so an untrapped cache and a trapped-but-undiscovered one look identical in the payload, and it is false again once the trap is disarmed or sprung. `inspected_by` is the party's own inspect-attempt history for that feature.
- `GET /api/games/{id}`: the same payload with the full transcript rebuilt from the event log. The client uses it on page reload.
- `DELETE /api/games/{game_id}`: abandon a session. It frees the in-memory store entry (404 for an unknown id, nothing on disk touched). The client calls it from "Abandon adventure" and when beginning a new adventure replaces a live session. The game and builder stores are LRU-capped (`_MAX_GAMES`/`_MAX_BUILDERS` in `app.py`) as hygiene, touched on access and evicted on insert.
- `POST /api/games/{id}/command`: one serialized osrlib command. Returns `accepted`, `rejections` (with friendly messages, prefixed by the acting character's name when known), the log delta, and fresh state.
- `POST /api/games/{id}/party/name`: body `{member_id, name}` renames one party member of a *live* session. Pre-game renames go through the builder's `rename` step instead. A bad name is a 200 with `accepted: false`. Success returns the full transcript re-rendered under the new name plus fresh state.
- `GET /api/games/{id}/narration?after=N`: LLM passages with `seq > N` plus the pending count. The client polls this while `narration.pending > 0`.
- `POST /api/games/{id}/save`: writes `saves/{code}.json`. Optional body `{name}` labels the save (stripped, ≤60 chars, blank means unnamed). Returns `{save_id, name}`: the stored name, or the derived one the summaries will show.
