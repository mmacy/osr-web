# The opening flow

- The client is a screen-state machine (`UI.screen` in `app.js`): `game`, and the overlay screens `title` (the front door), `library`, `staging`, `saves`, `menu`, `gameover`, `victory`. Game creation is **lazy**: browsing the library is client-side state, the staged party lives in a server-side party builder (`premade: true`), and the only `POST /api/games` is "Begin the adventure" (`beginAdventure`/`beginBuilderGame`, both of which call `enterGame`). Verify from the network log: flipping through every library entry must produce zero game POSTs.
- `boot()` lands in the game (or on its ending screen) when `localStorage['osrweb_game']` names a live session. With anything else (no id, or a dead id after a server restart) it lands on the front door with **nothing created** and the stale id cleared. The door's Continue restores the newest save, never a silent new game.
- Saves are named objects. The label is a top-level `name` key on the save file (the document envelope ignores unknown keys by contract, so old engines restore renamed saves unchanged), or it's derived server-side from adventure, place, and turn. Summaries contain exactly `save_id, name, adventure_name, saved_at, turn, place, party` (`tests/test_saves.py` pins the set). Rename preserves mtime so the newest-first order holds. The save list appears in exactly two places with distinct meanings: Load game (restore) and the staging screen's veterans tab (import). Both can prune: each has a per-save Delete, and Load game also has "Delete all" (`DELETE /api/saves`). Deleting the veterans tab's last save takes the tab with it, so the staging screen falls back to the premade party rather than leaving an empty picker.
- Every destructive verb goes through `confirmDialog`, whose message says what the verb costs, and each is the only one on its screen: "Abandon adventure" in the menu (`DELETE /api/games/{id}`, localStorage cleared, front door), Delete on a save, Delete on an adventure. The adventure dialog names the deletion's shape from the entry's `source_kind` ("the link … is removed — the files it points at are left alone" versus "its folder … with everything in it"), because those aren't the same act. The button renders only for `removable` entries, with no disabled ghost and no explanatory note. That's also why the library screenshot shows no Delete button: a capture library contains only the capture document, loaded through `OSR_WEB_ADVENTURE` and so never removable. `enterGame` also DELETEs the session it replaces. The in-memory game and builder stores are LRU-capped (`_remember`/`_touch` in `app.py`) as hygiene.
- **Both endings, game over and victory, route to the front door, and one shared constant names them.** `TERMINAL_MODES` (`game_over`, `victory`) mirrors osrlib's `SessionMode.terminal` and is the only place the client spells the ending modes. Nothing string-matches `game_over` on its own. `render()`'s trigger is the single router for every way into a session (boot, live play, restore). That's why `enterGame` shows the game screen **before** it renders. The trigger only fires while `UI.screen === "game"`, so rendering first (with the screen still `saves` or `title`) would drop a restored terminal session onto the live game screen with an empty action bar and a keyboard handler that returns, and no later render would rescue it. Game over offers two actions: roll a new party (same adventure, straight to staging with a fresh builder: `rollNewParty`, shared by both screens) or return to the title. Victory offers those two plus **Save the party**, which is victory-only by design. The topbar is unreachable under `#overlay` and Esc is the floor, so without that button the one party that finishes an adventure alive would be the one party the veterans flow can never import. A wiped roster imports as corpses (import strips every condition but `dead`), so the fallen's salvage door (placing a dead party in town for `raise_dead`) stays the referee's `PlaceParty`. The victory card also shows the fortune the party walks out with (`partyGold()` plus the valuables the sell card sums). Commerce is over, so that's a retirement purse, not a bug. The card shows the journal itself too, because `J` can't open the overlay from under `#overlay`.
