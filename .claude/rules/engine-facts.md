# Hard-won engine facts

osrlib owns every rule. These are the behaviors this app once got wrong, recorded so it doesn't get them wrong twice.

- `content.load_adventure` and `library.add_adventure` load an adventure document via `check_document(doc, "adventure")` (positional `expected_kind`, not a keyword) then `Adventure.model_validate(payload)`.
- Canonical edge keys are north/west only: a cell's south edge is `"{x},{y+1}:north"`, its east edge `"{x+1},{y}:west"`. The client mirrors this in `edgeAt()`.
- North is negative y. The bundled adventure's entrance is level 1, cell (2,15), and `EnterDungeon` always lands the party facing **north** (hard-coded in `_handle_enter_dungeon`, not authored).
- Only a thief's `pick_lock` can open a **locked** door. The engine rejects `force_door` on one with `exploration.door.locked` before the strength check is ever reached. After a failed pick, the engine writes a `lock_failures` entry and rejects that thief with `exploration.lock.locked_out` until they gain a level. A level-1 thief's chance is 15%. Never put content behind a locked door as its only route. The bundled document's one locked door (level 2, `4,4:north`) gates a *shortcut* into a room with two other ways in. `pick_lock` also only unlocks. `open_door` is still needed afterwards.
- Doors the party opened swing shut behind it (`DoorState.opened_by_party`), the secret door included. Walking back out of the captain's office needs a second `open_door`.
- `TakeTreasure` **distributes** a haul across the living members: items to a class that can use them, gems and jewellery balanced by worth, coins split denomination by denomination, and nothing loaded past the 1,600-coin maximum load. It emits one `ItemAcquiredEvent` *per member*, plus an `ItemsLeftBehindEvent` (`exploration.item.left_behind`) for whatever would not fit. That remainder stays in the cell as a pile. Anything reading that event stream has to treat a haul as the whole run, not one event. `server/narrate.py` collapses a run into one transcript line, and `narration._treasure_found` sums the run against its threshold. Naming `recipient_id` overrides the split and fills one pack. That is the one way a pickup can still overload someone. When it does, `move_party` rejects the *whole party* with `exploration.move.cannot_move`, and the fix is the sheet's give/drop buttons.
- A sprung trap can harm nobody, and `_resolve_trap` says so **only by emitting nothing**. A save that negates, an effect with no `damage_dice` (a `manual` or condition-only trap), and halved damage that floors to zero all emit `exploration.trap.sprung` and then stop. That is correct (HP really does not drop), but rendered bare the run reads "A trap springs on Flarg!" with no outcome. To give it one, `narrate.py` closes such a run with `_TRAP_NO_HARM` ("The trap does no harm.") after the victims' saving throws. The scan (`_harmless_trap_run`) walks the run of `saving_throw_rolled` events and judges by the first event past them against `_TRAP_CONSEQUENCE`. That set is deliberately wide, because with a member missing from it `narrate.py` would print a reassurance over a corpse. Keep the line: without it the LLM narrator, handed the same transcript as `just_now`, invents the injury the engine never dealt.
- Treasure is most of a B/X party's advancement, and osrlib awards treasure XP **on return to town** as one pool. `AdventureXpAwardEvent.treasure_xp` is the party's valuation delta since `EnterDungeon` snapshotted it, added to `monster_xp` and split evenly. The per-member `xp_awarded` lines state only the total. The tally line has to name both pools, or a return with treasure reads like a return with none. Selling is separate and later. `TreasureSoldEvent` names the price as **`gp_value`** (not `coins_gp_value`, not `value_gp`), and the sale changes no XP because the treasure already counted on the return to town. A wrong field name there renders every sale as `0 gp`, which reads like a worthless gem. Beside a tally line that names one pool, the two together read like an engine that values treasure at nothing. Handlers bind to event models by the `_on_{event_type}` naming convention alone, so a wrong field name raises nothing and renders a plausible number. `tests/test_narrate.py::TestHandlersReadRealFields` walks every handler's AST against its model's declared fields. Most tests in that file pass a `SimpleNamespace` built with whatever field names the test writer chose, so a handler and a test that agree on a wrong name pass together. That fixture can never catch this class of defect on its own.
- Generated area treasure (`AreaTreasureSpec`) lands as an engine-allocated cache with an engine id (`cache-0001`), on the cell the party stood on when the area was first entered. Content can't name it. A client has to read `cell.features`.
- Weapon templates have `damage` at the top level. Gear items (torch) have it under a `combat` facet. The client's `wieldedWeapons()` handles both. Keep it that way.
- Battle `resolve_battle_round` validates all-or-nothing: one bad declaration rejects the whole round, listing every rejection. The UI must surface which member failed. Better, it must never offer a declaration that can fail. See the declaration-menu fact below.
- osrlib's `EncounterView.battle_round` is `session.battle.round`: the rounds already **resolved**, not the round being declared. It is `0` when battle opens, and `1` straight after a surprise round the monsters spent attacking. `start_battle` resolves that free round immediately and advances the counter and the clock. For the *party's* free round it instead holds the monsters through round one and leaves the counter at `0`. The transcript's `— Round N —` prints the round being resolved, so `_current_battle_round()` in `app.py` adds one on the way out. The payload's `encounter.battle_round` is the round the party is declaring now, which is the number the declaration panel, the roundbar, and the transcript all show. `tests/test_battle_round.py` pins it on all three battle openings.
- Morale is a decision, so a group whose members are all incapacitated (asleep, paralysed, petrified) neither checks morale nor flees. The triggers stay pending until someone can act again. Fleeing is movement. When a routing group's living members are part mobile and part helpless, the runners keep the group and the helpless split into a new stay-behind group at the break distance (`battle.group.left_behind`, rendered by `narrate.py::_on_monsters_left_behind`). Keep that line, or the sidebar shows a second group that nothing in the transcript explains. A group with no mobile living member also never pursues a retreat or an evasion. The party's flight succeeds.
- In battle, `CastSpell` takes monster entity ids as `targets`, but the player view only names groups. `_fill_cast_targets()` in `app.py` resolves a `target_group_id` into living monster ids server-side (all for `hd_budget`/`area` modes, first for single-target). Don't move this to the client, which is never sent those ids.
- **The declaration menu offers only what the engine will accept, and it reads the round's shape off the engine rather than deriving it.** A round is all-or-nothing, so one illegal pick costs the whole party's turn. A back-rank thief's "Shoot — Dagger" at 5 ft, for example, is a melee attack from outside the front rank, and the engine rejects the whole round for it. osrlib 1.7.0 states the shape on `view.encounter` in four fields: `declarers`, `front_rank`, `immobile`, and `reloading`. `declarers` is the exact roster the command must name, living *and* able to act, so a slept or paralysed member is absent and a round naming them is `roster_mismatch`. `attackChoices()` in `app.js` turns those fields plus the group's distance into one legality verdict per wielded weapon. `declSelect` renders an illegal one **disabled with the reason in the label** ("Attack — Dagger (back rank)") rather than dropping it, because a weapon that silently vanished reads as a bug too. `declDefaults` picks the first legal one, so a one-click round is always a round the engine accepts. `renderParty()` recomputes the default every round, because a default that persisted would go stale the round after it was right (the party that closed in at 30 ft would "close in" again at 5 ft instead of swinging). Only a pick the player made by hand persists (`S.declPicked`), and only while it stays legal. There are three rules the client must not re-derive. First, **the front rank is as wide as the party's own fighting space**: five feet of frontage each, measured over the widest square of unbroken floor around the party (`_formation_width`). That means two in a ten-foot passage however far it runs, four in a room two cells square, and six in the dressing floor where the scripted fight happens. A fixed `i < 2` is wrong in both directions: it denies a rear member a legal swing in a room and offers a back-ranker an illegal one in a passage. Second, **the engine classifies a declaration by the weapon's `qualities` and the distance, not by which control sent it** (`_is_missile_declaration`). A weapon with both the melee and missile qualities (dagger, hand axe, spear) at ≤5 ft *is* a melee attack, and the menu labels it "Attack" there and "Shoot" beyond. Third, thrown arms max out short (30 ft), so `missileReach` checks `missile_ranges.long.max_feet`. The engine's own test is `distance <= long.max_feet`: maxima only, no minimum. `wieldedWeapons()` enumerates every weapon in hand, mundane template or magic arm, identified or not. The masked inventory (the inventory as the player sees it) reports a magic arm's base-weapon `qualities` and `missile_ranges` whenever the arm's masked display names that base weapon ("a dagger with a faint aura"), which is what makes a `dagger_plus_1` classifiable before it is ever identified. It reports neither field for an arm masked by category instead ("a staff"), because the display never named a weapon underneath it. So `qualities`, not `identified`, is the gate `wieldedWeapons()` reads, and the engine accepts a swing with an unidentified arm and identifies it on the first attack roll. `tests/test_declaration_shape.py` pins all of this, which matters because the client reads every one of these fields defensively (`enc.front_rank || []`). A projection that stopped including them would not raise. The client would quietly disable every attack in the game.
- Fog of war is engine-owned, and the engine remembers sight, not just footsteps. `view.explored[].cells` unions three sets: the walked cells, every cell the party's light has ever revealed, and the current light reveal. The revealed cells persist as `DungeonState.seen`, which is map memory only. Movement cost and pile visibility still key off walked `explored`. The client's `isExplored()` is the single predicate the automap and the wireframe viewport both read. Never accumulate seen cells client-side.
- The torch burn effect has `kind: "light"`. One dungeon turn is 60 rounds. Tinder box lighting is 2-in-6 per attempt. Long failure streaks are correct behavior, not a bug. The client collapses a streak of consecutive identical transcript lines into one line with a `×N` counter (`appendLog` in `app.js`). Narrative and place lines are exempt, and battle pacing passes `{ collapse: false }` so each beat stays its own line. The server transcript stays byte-identical.
- `content.py` rolls the pregenerated party with osrlib's stepwise creation functions rather than `create_character` itself, in `create_character`'s draw order (abilities, hp, gold). That lets the optional house rules (4d6-drop-lowest, max first-level hp) bend the draws. `content.py` also rerolls abilities for unmet class requirements (elf/dwarf/halfling) and walks kit tiers down for a small purse. Keep both paths when you edit the roster. The roster loop is `content.premade_members(stream, ruleset, house_rules)`, shared by two callers with different streams. `build_party` rolls on the session's own creation stream, which keeps `POST /api/games {seed: 42}` reproducible. `PartyBuilder.fill_premade` rolls on the builder's stream, which is what the staging screen shows and rerolls, with no session behind it. House rules for the premade party are an optional `house_rules` object in the `POST /api/games` body. The client persists the preference in localStorage (`osrweb_house_rules`) and also prefills the party builder with it.
- A new game opens at **turn 0 with an empty transcript and spells already prepared**. `content._prepare_spells()` is a creation-time affordance. It calls the core `memorize_spells` directly, which its own docstring sanctions for standalone use. Driving `PrepareSpells`/`Rest` commands instead would spend a night on the clock and write bookkeeping lines into the transcript before the player acts. The session's sleep ledger stays untouched, so the engine still rejects the first *in-game* `prepare_spells` until a night's rest (`magic.memorize.needs_sleep`), which is RAW (rules as written). Anything asserting on a fresh game's transcript must expect it empty.
- The narrator caches group/monster labels (`Narrator._labels`) because the terminal battle round renders after the engine clears `session.encounter`. Without the cache, raw `group-0001` ids leak into the transcript.
- Skeletons are immune to sleep (undead exclusion). A wasted cast is correct.
- Spell preparation is a full replacement, once per sleep. `memorize_spells` replaces the memorized list wholesale, and a successful `PrepareSpells` spends the sleep credit (`last_prepared_sleep[member.id] = sleep_count`) and six turns. A night's rest (48 turns) readies preparation and heals nothing. The engine applies natural healing on *day* rest only. `sell_treasure` pays full `value_gp` per item with no exchange spread, so the client's sell-button total is exactly the payout.
- `use_item` works on **magic-item instances only** (`inventory` lookup by instance id). Mundane gear never has a usable action, so the sheet offers Use only on magic pack rows. Mundane light is `light_source`, not `use_item`. Because using a potion or scroll consumes the instance *before* the events render, `narrate.py` names a used item from its identification line (`Narrator._item_labels`, fed by `_on_item_identified`). It degrades to the item's kind ("a potion") rather than ever printing an instance id.
- `reorder_party` is **silent**: an accepted reorder emits no events, so the re-rendered roster is the only confirmation. Don't synthesize a transcript line. The command must name exactly the current member ids, dead included. It is also what sets the battle front rank. The engine takes the rank off the head of the living marching order, as many as fit abreast in the party's fighting space. Reordering in town or while exploring is how a player picks who stands in the front rank.
- `EdgeView.door_wedged` crosses the wire, and the spike holds a door against **swinging shut**. `close_door` rejects with `exploration.door.wedged` (and there is no un-wedge verb), but `open_door` on a wedged-shut door still succeeds. The party may pull past their own spike, and the door then stands wedged open. The UI disables only Close for a wedged door. Disabling Open would invent a rule and softlock the route. `wedge_door` works on a door open or shut, takes any living member's `iron_spikes`, and consumes one. The engine rejects a second wedge (`exploration.door.wedged` again).
- A fresh premade level-1 cleric has **zero spell slots** (B/X clerics pray for nothing at level 1), so exercising the exploring cure flow needs level 2 first. The route is `award_xp` ~2000, then Rest the night, then Prepare. A cast consumes the memorized copy.
- Party import (`content.party_from_save`) goes through `load_game(document).party`, which gives it migrations and version checks for free. It then strips conditions with a non-`None` `effect_id` and all `stat_modifiers`, because those are owned by the old session's effects ledger, which the new session doesn't have. Only `dead` survives (written by osrlib's rules kernel, `osrlib.core`, with `effect_id: None`). It also strips **every carried instance whose template is not in the shipped catalogs** (`_shipped_item`, filtering `items`, `worn_armour`, `shield`, `wielded`, and `rings`). Valuables and the purse are money and stay. The reason is that `has_item` is stateless and party-wide, dead members and worn slots included. A veteran carrying one adventure's key would otherwise walk into the next one, or a re-run of their own, with a `has_item` gate already satisfied. Adventure-bound objects stay with their adventure.
- `GameSession.new` keeps member ids a loaded party already has, but the fresh session's `IdAllocator` starts at zero. `content._advance_allocator` fast-forwards its counters past every `character-`/`valuable-`/`magic-item-` id the imported party already has. Without that, later allocations would collide.
- The party builder (`server/creation.py`) drives osrlib's stepwise creation functions itself for structured rejections. Draws follow `create_character`'s fixed order per character (six ability scores, hp, gold). Optional house rules (`HouseRules`) are set before the first character is rolled and locked once one is. They bend two draws. 4d6-drop-lowest takes four dice per ability instead of three, and max-HP skips the hp draw entirely (the builder computes die-max + CON modifier, floored at 1). An optional caller-supplied seed (`PartyBuilder(seed=...)`, `POST /api/party-builders {"seed": N}`) replays those draws exactly for a given step sequence. That is what makes the wizard testable and a rolled character's screenshot stable. A reroll after `discard` draws on down the same stream rather than repeating the scrapped character, so it stays reproducible too. That seed is the builder's alone: never a game session's master seed, never derived from one, never in a response. No determinism contract breaks: the master seed is still private and never reproduced against `create_character`. Class and adjustment lock once hp is rolled (the hit die and CON modifier are spent). The builder replays purchases into a fresh `Inventory` on every read, which is what makes creation-time returns (and all-or-nothing `buy_kit` sets) free. `builder.party()` deep-copies members so an abandoned builder never shares mutable state with a session. Game creation consumes the builder.
