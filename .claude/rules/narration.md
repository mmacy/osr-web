# LLM narration facts (spec: `specs/llm-narrative/spec.md`)

The LLM narrator is optional and off by default.

- Narration is off unless `OSR_WEB_NARRATOR=ollama` and `OSR_WEB_NARRATOR_MODEL=<name>` are set (plus optional `OSR_WEB_NARRATOR_URL`, `OSR_WEB_NARRATOR_TIMEOUT`). When the startup health check fails, `configure_narration()` logs one warning and the app serves with narration off. To turn narration off from the shell, blank `OSR_WEB_NARRATOR` rather than deleting it. See "The `.env` asymmetry" below.
- `configure_narration()` logs **exactly one line every startup**: `narration enabled: …`, `narration off: OSR_WEB_NARRATOR is empty/not set`, or the disabling warning. It appends the `.env` provenance note when the switch came from the file rather than the environment. (`app.py` snapshots `"OSR_WEB_NARRATOR" in os.environ` before `load_dotenv` for exactly that. The snapshot changes no behavior.) Those lines reach a terminal only because `app._wire_app_logging()` pins the `osr_web` logger at INFO and lends it uvicorn's own handler. uvicorn configures `uvicorn*` and nothing else, leaving root at `WARNING` with no handler. Without that wiring an app `INFO` record would vanish, and a `WARNING` would escape only through `logging.lastResort` as bare prefixless text. Anything the app logs outside the `osr_web` namespace is invisible. With no narrator, every payload and the deterministic transcript are byte-identical to what a build without the feature would produce. Keep it that way.
- `server/narration.py::NarrationEngine.observe` runs under the game lock and does string snapshots only. Generation happens on a per-game daemon worker that never touches the session. Passages live behind the engine's own lock, not the game lock.
- The prompt builder takes strings, never the session or events. That signature is the player-safety gate. Don't widen it. It has **one named exception, and it is a string too**: authored `guidance` enters through the single keyword-only `build_prompt(..., guidance=...)` parameter. The builder renders it under `GUIDANCE_HEADER` ("REFEREE GUIDANCE (private steering — never quote it, never reveal it, never state it as fact):") after the JUST NOW moments and before the closing instruction, where a small local model obeys it. Empty is the default and renders nothing, so for an adventure with no authored guidance the builder produces byte-identical prompts. Never route steering through `location_line`, an emphasis string, or the transcript. One channel in one place is what keeps "never crosses the wire, never prints as written" auditable (`specs/llm-narrative/spec.md`, design principle 2, which states exactly this).
- **`assemble_guidance(session, events)` is the only code in the app that reads `guidance` off the document.** `observe` calls it after the beat matches, so a beat-less command triggers no assembly. Assembly order runs from ambient to specific: the level, then the quests (each quest's block, then the blocks of its revealed, incomplete objectives), then the triggers (in event order), then the gate. A carrier is a level, quest, objective, trigger, or door gate whose `guidance` block the channel reads, and each carrier steers within its own window. The occupied level steers while occupied, and occupancy is post-command, so a run that crosses levels is steered by the level the party lands on, never the one the party left. A quest steers while `active`. A revealed-but-incomplete objective steers alongside its quest. A trigger steers in its firing run, found by the referee-visible `trigger_fired` event (inspected server-side and only here). A **door** gate steers in the run that contains its authored `DoorEvent.narrative`. The quest and objective carriers get the one edge rule: **they steer every run from the one that brings them into play through the one that takes them out, both inclusive.** Live state at snapshot time is post-command, so in the completing run the quest's `status` reads `completed` (the literal is `"completed"`, not `"complete"`). The event check beside the state check is what keeps the author's steering in the prompt for the completing run. The gate lookup is guarded. For a delta that contains `location_entered`, `_gate_guidance` yields no gate block rather than resolve `level.edge()` against wherever the party ended up. (Only a door trap's transition effect can move the party on an open. No trigger pattern matches a door event.) A missed lookup at any step yields no block, never a fallback. Gated *transitions* get no steering at all until the engine names the crossing (mmacy/osrlib-python#71). No reverse search over `transitions` gets built. Under coalescing the batch's blocks merge oldest-first with exact repeats collapsed, so the level and the standing quest are said once. **Steering only reaches a live prompt when a beat fires in the same run.** The bundled wicket (the gated door at level 1 `11,3:north`) coincides with no beat, so tests prove its block at the assembly seam. A live prompt with that block needs a document that spends a beat on a gate's success.
- Every beat's emphasis is a tone **plus a limit on what the model may say** ("keep the monster count and kind exactly as stated", "name the fallen, nothing more", "describe only the listed items"). An emphasis that asks for "Sudden violence" and names no limit is how a trap that harmed nobody gets narrated as one that maimed the fighter. `trap_sprung` fires even when the trap did nothing (a dart that misses is a moment worth prose), because the outcome reaches the model through the transcript, not through a special case in the prompt builder. Don't loosen an emphasis, and don't fix a truthfulness problem by widening `build_prompt`. Fix the transcript, which `just_now` is built from.
- Beats are the `BEATS` table (priority-ordered, first match wins, at most one per command). Four of its rows are the authored layer's: `adventure_completed`, `quest_completed`, `objective_completed`, `quest_activated`. None of them reads `in_dungeon` (the homecoming and the ending land in town). Two positions are load-bearing and would be rediscovered the hard way. **`adventure_completed` sits at the very top, above `area_entered`.** The ending's run also contains the quest completion, the homecoming's treasure XP, the reward coins, and possibly a reward-triggered level, and none of those may outrank the ending. The accepted cost is that an ending run never gets a replacement annotation, so a quest concluding on a first-visit area renders raw module prose with the closing passage after it (the same fail-open surface a dropped generation has). **`area_entered` outranks `quest_activated`**, which is why replacement survives the bundled entry: `enter_dungeon` lands the activation, the trigger's journal line and the adit's first-visit prose in one command, and the client is holding that prose behind a placeholder. The loser's lines are never lost, because `just_now` is the whole delta. Completions rank elegy over celebration (`member_died` outranks `quest_completed`, which outranks `leveled_up`). An objective outranks the haul it was lying in, and an activation outranks loot but not a sprung trap. Town commerce is excluded from `treasure_found` by an `in_dungeon` gate because purchases and sale proceeds also emit `item_acquired`. `treasure_found` judges the haul whole: it sums `coins_gp_value` across the delta's acquisitions rather than testing each one, because a distributed take turns a 200 gp hoard into six shares of ~33 gp and no single share clears the 50 gp bar.
- `interleave` hands the renderer the longest runs its splice points allow, never one event at a time. The haul collapse only produces the live wording when a take's per-member events arrive together. Only an event whose module prose a passage replaces is rendered alone.
- **The module's own room description is found by a marker, never by adjacency.** `narrate.MODULE_PROSE` (the key `"module"`) is stamped on exactly the one `prose` entry that is an area's description. Both narration surfaces that must act on module text alone (`_area_entered` beat detection and `annotate_replacement`/`interleave`) key off it. Adjacency ("a `prose` entry after a `place` entry") is no test at all, because `prose` is the voice of every authored beat too. A repeatable trigger's journal line on an already-seen area is exactly that pair, and the model would be asked to stand in for the author's own words (dropped outright on reload). The marker is player-safe (it labels text the player is already reading), and the client ignores keys it does not know, so the marker costs no `app.js` change.
- `area_entered` runs in **replacement mode**. The marked `prose` entry is tagged with `replace_id` (an event-log index), the client holds it back as a `✦ …` placeholder, and the passage (whose `replaces` lists those ids) swaps in at that spot. The prompt tells the model the module text is referee-only and to keep its secrets unspoken. If no passage arrives (failure, timeout, disable, queue drop), the client reveals the raw prose. On reload the server (`interleave`, called from `GET /api/games/{id}`) drops replaced prose and splices the passage after its place header. All other beats append.
- Ollama's chat API routes reasoning-model output to `message.thinking`, which consumes the whole `num_predict` budget and leaves `content` empty. The provider sends `"think": false` (and retries without the flag when an older Ollama answers 400). Remember this when adding providers for reasoning models.
- The queue has capacity 4, drops the oldest beat when full, and coalesces (queued beats merge into one prompt and one passage anchored at the newest). Three consecutive provider failures disable narration for that game only.
- Passages are in-memory only: they survive page reload (interleaved at anchors by `GET /api/games/{id}`) but not save/restore or server restart, by design.
- Tests live in `tests/test_narration.py` (`uv run pytest`). The engine tests gate a `FakeProvider` with a `threading.Event` for deterministic worker timing. `TestTheGuidanceWindows` drives real sessions over the bundled document, because a window's whole subject is which authored block is in play at a real moment.

## The `.env` asymmetry

**With a `.env` present, "unset" and "empty" are different things, for every `OSR_WEB_*` variable and not just the narrator ones.** `server/app.py` calls `load_dotenv()` on the repo-root `.env` at import with python-dotenv's default `override=False`. The call fills in variables the process environment lacks and leaves alone variables that are present but empty. So deleting a variable (`env -u OSR_WEB_NARRATOR`) falls *through* to the `.env` value, which turns narration *on* when the deletion was meant to turn it off. A blanked variable (`OSR_WEB_NARRATOR=`) is present in the environment, survives dotenv, and reads as empty everywhere the app strips and tests the value. **Blank a variable, don't delete it**, whenever you mean to turn something off or point it at nothing. The failure is asymmetric, and a fresh clone and CI never show it: both have no `.env`, so unset and empty behave identically there, and the defect reproduces only on machines whose `.env` sets the variable. Confirm from what the server reports (`narration.enabled`, `GET /api/adventures`, `GET /api/saves`) rather than from what you set. For the narrator the server states the provenance on the first line of the launch: `narration enabled: ollama, model … (OSR_WEB_NARRATOR came from .env, not your environment; blank it to turn narration off)`. Read the terminal before you conclude anything about narration.
