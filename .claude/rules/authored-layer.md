# Authored-layer facts (spec: `specs/authored-layer/spec.md`)

osrlib's authored layer (gates, data-authored triggers, the journal, quests, victory) shipped in 1.5.0, and objective display names followed in 1.6.0. The floor `pyproject.toml` declares is 1.7.0. All four of the spec's phases are in the app: the engine's voice in the transcript, the journal and quest UI, the two ending screens and the concluding quest that makes the default adventure winnable, and the narrator's four authored-layer beats plus the authored guidance channel (recorded under "LLM narration facts").

- **The interpreter is registered in `Game.__init__` and nowhere else.** All four session routes (premade, builder party, veteran import, save restore) converge on that constructor. Listeners are code, which a save never contains. `register_listener` never dedupes, so a second registration fires every trigger twice. Registering in `content.py` would miss the restore path. Forgetting it entirely is *silent*: gates still work (they are in-engine legality checks), but no trigger fires, no quest advances, and an activation-less quest sits in the view reading `active` forever.
- **An authored gate refusal renders verbatim.** `rejection_text` reads `params["refusal"]` first. The engine sets that key on `exploration.door.gate_refused` and `exploration.transition.gate_refused` rejections, and only when the author wrote a refusal. The mapped `_REJECTION_TEXT` line is the unauthored fallback and never competes with the authored one. `app.py`'s rejection assembly prefixes a speaker name only when `params` include `character`/`caster`. Gate refusals never do (a door gate's params are `{direction, refusal}`, a transition gate's `{refusal}` alone), so the author's sentence reaches the player unprefixed and byte-exact.
- **`Narrator._equipment` is `session.effective_equipment`**, not `load_equipment()`. `effective_equipment` is the engine's own resolver for authored ids (the shipped catalog plus the adventure's bundled templates). Against the shipped lists alone, every line naming a bundled item would print the raw id. For an adventure bundling nothing, `effective_equipment` *is* the shipped catalog.
- **`_area` resolves off the event's own `dungeon_id`/`level_number`/`location_id` and never the session's location. There is no fallback.** Because rendering happens after the whole command completes, a walk from the session's location would resolve every area event in a delta against wherever a trigger consequence had since put the party, and a whole-log re-render (a rename) would resolve all of history against the final location. An event with no `dungeon_id` (a pre-1.5.0 save's persisted log) renders **nothing at all**, not even a place header. The area never enters `seen_areas`, so the party's first arrival there after the upgrade re-prints the description in full. Restoring that scrollback fidelity, if it is ever wanted, is osrlib load-time normalization. It is never an osr-web fallback.
- **`item_consumed` is not gated on authored content.** It fires for a gate's toll *and* for `WedgeDoor`'s iron spike, so a verb that authors nothing emits it too. `WedgeDoor` emits exactly `[ItemConsumedEvent, DoorEvent(exploration.door.wedged)]`, and `_is_wedge_spike` drops the first, because the door line already names the spike. `_is_wedge_spike` is keyed to the wedged *code*, not to `iron_spikes`, so a toll paid on the way through a door still reports. A magic toll's event names, as its `item_id`, the `instance_id` of an instance already consumed by render time. `_consumed_item_phrase` looks that id up *explicitly*: in effective equipment, then the packs (a toll from a magic stack decrements the stack and leaves the instance carried), then `_item_labels`. It degrades to "an item", never an id. `_consumed_item_phrase` does not decide the lookup failed by comparing the answer to the id it passed in. An adventure may bundle `{"id": "rope", "name": "rope"}`, and that comparison would throw a perfectly good name away.
- **The completion beat renders on `quest_completed` only.** A concluding quest emits `quest_completed` then `adventure_completed` with the *same* authored line as its `narrative`, and the engine appends that line to the journal once. `_on_adventure_completed` renders the terminal fact alone, naming the concluding quest off `AdventureCompletedEvent.name`.
- **Objective and quest labels come off the event, and osr-web never second-guesses them.** `ObjectiveSpec.name` is authored and optional (osrlib 1.6.0, mmacy/osrlib-python#66). `ObjectiveView.name` is `name or id`. Both objective events (`objective_revealed`, `objective_completed`) include `name` and `quest_name`, and `AdventureCompletedEvent` includes the quest's `name`. The handlers render the authored beat when there is one and otherwise state the fact by name (`New objective: {name} — {quest_name}.`, `Objective complete: …`). The quests card (`buildQuestsCard`, one card for every active quest, in the exploring rail and first in the town board's card grid) renders `ObjectiveView.name` verbatim, slug included. The engine fills `name` with `objective.name or objective.id`, so an unauthored objective's label *is* its id. Comparing the two to guess whether an author wrote one only throws a good label away, the same anti-pattern the `_consumed_item_phrase` bullet records above. No slug-prettifying workaround gets built here. If a slug is ugly, the fix is an authored name in the document.
- **`osr_web.referee` is the referee's channel** (`app._log_referee`, called on every command's log delta). `_log_referee` logs `trigger_fired` at INFO with its authored `fired` beat, and `note_recorded` at WARNING (dropped consequences, unlandable rewards, truncated cascades). The channel reaches the operator's terminal because `_wire_app_logging` pins the `osr_web` namespace at INFO. It never crosses the wire, and it is the only consumer a trigger's `fired` beat gets. **Every interpolated value goes through `_one_line`.** Trigger ids, beats, and note text all come out of an adventure document, and an uploaded document is content the server did not write. A newline in any of them would let the document's author forge whole lines on the one screen this channel is trusted on.
- **`validate_adventure` runs at load and at upload** (`content.load_adventure`, `library.add_adventure`), not just inside `GameSession.new`. Without that validation a document with an authored typo loads clean and shows in the library. The failure then surfaces only at Begin the adventure, where `GameSession.new` runs the same walk. `ContentValidationError` maps to a 422 whose `detail` is the error's message (`app.py`'s exception handler). The library *scan* stays metadata-only by design.
- **A found room trap states no bearing, and reconstructing one is not allowed.** A `room_traps` search covers the searched cell's door edges too, so a find can be a trap in the room beyond a door the party has not opened. The phrase "a hidden trap" sometimes reads as a trap underfoot when it is not. Naming the door fails two ways. First, `SearchCompletedEvent` has no position field, so any render-time reconstruction reads the party's *current* cell, which on a whole-log re-render (reload, rename, restore) is not the searched one. On the bundled document, a trap found underfoot would come back as "a trap rigged to the south door". Second, no host-side walk can honour `_reveal`'s own guards, so such a walk could point at an undiscovered secret door and leak hidden geometry. `_found_phrase` is deliberately a **module function taking a token alone**: it cannot reach a session even by accident. A bearing arrives only when the engine puts one in the token (mmacy/osrlib-python#67). There is no interim approximation. The rule is the same as for `_area` and for the level-arrival line below: render what the event states.
- **A level arrival never says which way the stair ran.** "The party descends to level N" would be a guess, and the bundled up-stair (level 2 to level 1) makes it a false one: the party climbs and the transcript would say otherwise. `LocationEnteredEvent` states which level was reached, not by what means. The previous level is not something a whole-log re-render can reconstruct without guessing. The wording is neutral ("The party comes to level N.") until the engine states the direction (mmacy/osrlib-python#68).
- **Two more gaps are filed rather than worked around, for the same reason: don't re-derive what the engine declines to state.** A quest's `grant_coins` reward to `@party` expands to one command per living member. Each emits a bare `ItemAcquiredEvent` byte-identical in shape to a treasure share (no `source` stamp, no grant marker), so `narrate.py`'s haul collapse reports the headman's per-head payment as one pot split. The sum is right and the framing is wrong. Every discriminator that does not guess lives in the session or its mode, and a mode test at render time would re-word every *historical* haul on a whole-log re-render (the `_area` defect again). The wording changes only when the engine stamps provenance (mmacy/osrlib-python#70). A gated **transition**'s success beat is the `narrative` on the arrival's `LocationEnteredEvent`, which names where the party arrived and nothing about the crossing it took, so transition gates get no narrator steering at all (mmacy/osrlib-python#71). The only mapping available would be a reverse search over `transitions` filtered by destination and tie-broken by comparing authored text to the event's `narrative`. That is exactly the second-guessing of an engine answer this section already records three times.
- **A `victory` save pins the engine floor.** `SessionMode.VICTORY` is a value pre-1.5.0 engines do not know, so a save written at victory is unreadable by anything older (osrlib's documented accepted risk for a new enum value). The victory screen's Save the party makes such saves routine. No player runs a downgraded engine against their own saves, but a developer bisecting with an old checkout might, and the refusal is the diagnosis.
- `view.journal` and `view.quests` cross the wire with **zero server change**: `_state` dumps the whole player projection and never enumerates view fields. `guidance`, `trigger_fired`, `note_recorded`, the trigger fired-marks (`fired_triggers`, the engine's record of which triggers have fired), and quest wiring never cross, and no referee endpoint exists or will.
